## 一、瑞幸入表

### 1.1 这轮真正的坑不是"加个品牌"

把瑞幸加进 `BRAND_S` 是一行代码。但**只做这一行会引入两个静默错**——都不报错，只是结论错：

1. **「0 加盟费」被说成「查不到」**。旧代码是 `if fee:`，`0` 与 `None` 都走 else 分支。
   于是对瑞幸——**全市场最出名的"不收加盟费"品牌**——系统会答"暂无公开加盟费口径"。
   那是**假话**，而且是最容易被用户当场戳穿的一类假话。
2. **物料率套品类级 32%**。奶茶品类 `MATERIAL_RATIO['奶茶']=0.32`，而瑞幸 2025Q3 CFO
   披露原材料占总净营收 **36%**（券商测算毛利率 63.8% 互相印证）。
   用 32% 会**低估成本 4 个点**，回本周期系统性偏短——**结论方向是错的**，不是"略偏乐观"。

所以本轮的落点是**把"0 与 None 区分开"和"品牌级成本覆盖"这两条口径补齐**，而不是加一行品牌名。

### 1.3 为什么 `BRAND_S=2.2` 而不是 2.5

瑞幸门店 31,048 家（2025 年报），按"门店量级"该进 3 万+ 档（蜜雪 2.5）。
**但它在奶茶品类里只有部分产品线（轻乳茶/茶咖/果咖）与奶茶店抢同一杯需求**，
所以给 2.5 会**高估它的分流强度**。取 2.2（=古茗档）是**保守**方向的判断值，
并在代码注释里明确标注这是"分档判断值、非逐店标定"。

### 1.4 "配不齐"怎么处理的：唯一没标的字段如实留空

`docs/欧文五条需求-方案待审批.md` 列的瑞幸字段清单里，有一项**没有标定样本**：
**同商圈溢价 UPLIFT**。本轮决定：

> **`UPLIFT` 里不放瑞幸** → `brand_uplift_detail()` 返回 `uplift=1.0 / TIER3 / ci=None / n=None`，
> 即"识别出品牌但未收录"。**不拿别的品牌的值顶上、不拍脑袋给 1.05、不用品类均值。**

门禁 `§15` 第 ② 组专门钉这一条：`check('瑞幸' not in UPLIFT, ...)`。
理由：uplift 是**比值**，需要同商圈内多个样本；n=0 时任何非 1.0 取值都是编的。

> 注：`expand_sample.py`（§二）**已经能算出**瑞幸的扩样 uplift（n=45，raw 1.1291，收缩后 1.1162）。
> 但**是否据此把瑞幸从 TIER3 提到 TIER2，要欧文点头**——理由：咖啡门店与奶茶门店
> 同商圈竞争，口径上说得通但**不同源**；且本地库覆盖不完整（L1），
> 应先把 uplift 当"同商圈相对水平"看，而不是流水倍数。

### 1.5 实证（同点位对照）

以杭州湖滨 in77 商圈、月租 ¥20,000、35㎡ 的一点位测同一家店：

| 品牌 | 物料率 | 月物料 | 回本周期 |
|---|---|---|---|
| 蜜雪冰城 | 0.32（品类级） | ¥39,802 | 21.4 月 |
| 瑞幸 | **0.36**（品牌级） | ¥44,777 | **27.0 月** |

差 5.6 个月全部来自物料率那 4 个点——**这就是 1.1 第 2 个坑的具体量级**。

### 1.6 做实机验证前读代码，又抓到同一个坑的**第二处表面**

1.1 说的"0 被当成查不到"，本轮在 `agent_graph.py`（**聊天提示**）修好了，
`§15` 断言也全绿。但跑实机前顺手读了一遍链路，发现 `app_chainlit.py:336`
构造**投入表单 note** 的那段，仍是老的两态写法：

```python
if jf and jf.get('fee'):        # ← 瑞幸 fee=0 是 falsy
    ... 投入不得低于此数（低于需确认）
elif brand:
    inv_note += f'　｜　{brand} 暂无公开加盟费口径，不做下限校验'   # ← 假话还在这里
```

也就是说：**聊天里说"明确不收加盟费"，同一个屏幕右下角的表单上却写"暂无公开加盟费口径"。**
一处改好、另一处没动 —— 与"知识库两处表面"（`knowledge.py` / `KB_THEORY`）同源的
高发错，只是这次的第二个表面藏在 UI 的 payload 构造函数里。

修法与后端一致（按 `status` 三态分派：`none` → "明确不收加盟费，此项不做下限校验
（品牌方按门店月毛利阶梯分成，需另行核算）"；`amount` → 原下限文案；`unknown` → 暂无口径）。

**为什么静态断言没抓住它**：`§15` 当时验的是 `get_join_fee()` 的**返回值**，
而 `app_chainlit.py` 是**消费方**——返回值对、消费方用错，断言照样全绿。
本轮补的三条断言就是钉这个消费方：

- `'status' in APP and "== 'none'" in APP` —— 必须按三态分派；
- **顺序断言**：`jf.get('status')` 必须出现在 `jf.get('fee')` **之前**。
  > 这里刻意不用 `"jf.get('fee'):" not in APP` 这种字面断言——新写法里
  > `elif jf and jf.get('fee'):` 本来就含这个子串（`elif` 里还带着 `if`），
  > 字面查会**自己打自己**。顺序断言才能真抓回退：一旦改回只写
  > `if jf and jf.get('fee'):`，`jf.get('status')` 整个消失 → 必 FAIL。
- `'暂无公开加盟费口径'` 必须排在三态判断**之后**（排在前面 = 它在三态之外，瑞幸会掉进去）。

实测偏移：`status@8460 < fee@8629 < 暂无@8916`。

实机侧另加了 `live_ui_probe.py §16`，直接读表单 `innerText` 断言
"有『明确不收』且**无**『暂无』"——因为**静态断言永远验不出"这句话在屏幕上不对"**。

## 二、样本扩量：83 家 → 796 家

### 2.1 根因：不是数据不够，是当初只标了 3 个商圈

`stores_calib.csv` 的 83 家，商圈分布是：

| 人工商圈 | 门店数 |
|---|---|
| 杭州湖滨 in77 | 39 |
| 宁波天一广场 | 27 |
| 海宁银泰商圈 | 17 |

**只有 3 个。** 而 `calibrate_anchor.py` / `calibrate_brand_uplift.py` 算 D 与 P 用的是
`data.query.query_within`——**纯本地 SQLite，不是高德实时**。
也就是说：**标定样本的原始材料本来就在本地库里**，当初只是手抄了 3 个商圈。

实测本地库（`data/zj_poi.db`，9 类 POI、11 个地市）：

| 指标 | 实测值 |
|---|---|
| 奶茶 POI | 3,959 条 |
| 其中**能识别出品牌**的 | **2,551 家 / 34 个品牌**（原样本的 31 倍） |
| 商圈 POI | 3,466 条 |

### 2.2 做法：`src/analysis/expand_sample.py`（零 API）

1. 枚举**全部**能识别品牌的奶茶门店；
2. **商圈锚定**：每店归属"1 km 内最近的『商圈』POI"；
3. 按**引擎同口径**算 D（0.8×学校+办公+社区 + 0.2×商圈，500 m）与 P（Huff，λ=2.0、d0=50 m、品牌 S）；
4. 按品牌算 uplift（同商圈内 `DP/商圈中位`，K=5 收缩，clamp (0.80,1.25)）；
5. 与引擎在跑的 `brands.UPLIFT`（83 家标定）**逐一对照**。

实现上有一处必须说清的工程决定：**加了一个 0.01° 分桶的空间索引**（`Grid`）。
原因：`query_within` 每次全表扫描该 category 再逐行 haversine，2,551 店 × 4 个 category
= 上亿次三角函数，跑不完。所以用网格做**预筛**、命中后再用**同一个 `haversine`** 判定。

> **这个加速有没有偷改结果？** 由 §2.4 校验 A 硬性对拍，**不许靠"看起来对"**。

### 2.4 校验：扩样管线真的和标定管线同口径吗？

`_expand_report.txt` 的 §4 是**三段式硬校验**（不是自说自话）：

**A. Grid 加速管线 vs 原 `capture_share`（真 `query_within` 路径），83 家逐店对拍**

```
|ΔD| 最大=0.000e+00   |ΔP| 最大=1.110e-16   完全一致 83/83 家
✅ 逐店完全一致 ⇒ 没有第二套规则，扩样与标定同口径
```

（`1.110e-16` 是双精度浮点的末位噪声，不是差异。）

**A2. 存量标定产物是否还跟得上当前代码**

跑第一遍时发现 `anchor_calib.csv` 有 **1 家不一致**：`贡茶gongcha888(新街店)`，
存量里 `own_S=1.0`、现算 `own_S=1.4`。原因**不是标定错了**，而是**品牌表后补**——
贡茶是在该文件生成之后才进 `BRAND_KEYWORDS` 的，`own_S` 由 1.0 升到 1.4，
分子变大 → P 由 0.4286 升到 0.5122。

> **教训**：存量标定 CSV **不会自动跟着代码走**。所以本脚本一律**实时重算**，不读旧 CSV。
> 重生成后 A2 报 0 家漂移。

**A3. 引擎写死的锚点常量，今天还复现得出来吗？** —— 见 §三。

**B. 商圈口径对照（这是本轮最重要的局限）**

```
原人工商圈 3 个：宁波天一广场(27家) ｜ 杭州湖滨in77(39家) ｜ 海宁银泰商圈(17家)
→ 代理商圈（最近商圈 POI ≤1000m）32 个
   杭州湖滨in77(39家) 被拆到 16 个代理商圈
   宁波天一广场(27家) 被拆到 14 个代理商圈
   海宁银泰商圈(17家) 被拆到 2 个代理商圈
```

**粒度不等价**：原人工商圈是"大商业区"（27~39 家/组），代理商圈是"最近单个商圈 POI"。
而 uplift 是"**对同商圈中位取比值**"——分母口径一变，点估计必然移动。

⇒ 所以 §2.3 的漂移**同时含"样本量增加"与"分组变细"两个因素（混杂，未分离）**。
**不能**把它解读成"旧结论错了"，也**不能**解读成"扩样只是加了样本量"。

### 2.5 局限声明（必须随结论一起说）

| # | 局限 | 实测证据 / 后果 |
|---|---|---|
| **L1** | **本地库覆盖不完整，且随商圈变化** | in77 点位库内 19 家奶茶 vs 高德实时 49 家（**39%**）、另一点位 9 vs 28（31%）；天一 65%/95%。<br>⇒ 扩样后的 **D×P 绝对水平不能当新锚点**（是水平偏差，不是随机误差）。<br>⇒ 本脚本**刻意不产出**替代 `REF_DP`/`P_REF` 的新锚点。要动锚点必须先"补库"或做"库→实时"校正。 |
| **L2** | 商圈口径是**代理**（最近商圈 POI ≤1km），非人工商圈边界 | 见 §2.4 B：3 个 → 32 个，粒度不等价 |
| **L3** | 品牌识别依赖 `BRAND_KEYWORDS` | 识别不出的连锁仍按"个体/杂牌"参与竞争 |
| **L4** | 高德搜索类配额：**个人 key 100 次/日** | 且实测有 QPS 限制（连续快发报 `CUQPS_HAS_EXCEEDED_THE_LIMIT`）。1 次 `place/text` 可换"一个品牌在一个城市的真实门店总数"，但拿坐标要按 25 家/页翻页 |
| **L5** | 引擎锚点常量与注释口径不符 | 见 §三（**只报告，本轮未擅自改**） |

### 2.6 所以"怎么大量增加真实样本"的答案

1. **已经加了，零成本**：83 → **796 家（×10）**，不需要一次高德调用。
   因为标定本来就走本地库——**"样本太少"是标注口径问题，不是数据缺口**。
2. **但它买到的是"功效"和"稳健性复核"，不是"新锚点"**。绝对水平受 L1 限制。
3. **真正要"更多真实数据"的下一步只能靠补库**，而补库的瓶颈是 **L4 的 100 次/日配额**：
   - 按 11 个地市 × 主要品牌 × 25 家/页 翻页估算，需要的调用量远超个人 key 日配额；
   - 因此**短期可行的做法**是：先挑"N 家以上品牌门店"的商圈做**定向补库**
     （本地库已有 119 个 n≥5 商圈），而不是全省铺开。
4. **要动锚点（`REF_DP`/`P_REF`）之前，必须先解决 §三 的两个问题**，
   否则"重标定"得到的新值同样不可复现。

## 三、顺带查出的两个遗留问题（只报告，未擅自改）

这两条是本轮**为了做同口径校验而查出来的**，不属于欧文本轮诉求。
**我没有改引擎常量**——改锚点会改写**全部历史结论**，必须欧文点头。

### 3.1 锚点常量的口径与注释不符

`src/engine/scoring.py` 写死 `REF_DP=6.2489` / `P_REF=0.5012`，注释说：

> 这两个值由 `calibrate_anchor.py` **同一次运行**产出，
> 口径必须一致（同为"品牌一致 + **全样本中位** + 未做密度调整"）。

**实测结果：**

| 项 | 值 | 说明 |
|---|---|---|
| `calibrate_anchor.py` **今天**实际输出 | `REF_DP=5.85` / `P_REF=0.5074` | **全 83 家**口径 |
| 实测 D×P 中位（**全 83 家**） | **5.8489** | 与上面一致 ✅ |
| 实测 D×P 中位（**剔低证据点后 77 家**） | **6.2489** | **与引擎逐位一致** ✅ |
| 实测 P 中位（剔低证据点后 77 家） | **0.499702** | 引擎 0.5012，**差 +0.0015** ⚠️ |

**结论：**
- `REF_DP=6.2489` 的**数值本身每项都能复现**，但它实为**"剔除 6 个低证据点后 77 家"的中位**
  （即 `calibrate_brand_uplift.py` 的口径），**不是注释写的"全样本中位"、也不是
  `calibrate_anchor.py` 的输出**。→ **错的只是注释里的出处与口径。**
- `P_REF=0.5012` **复现不出来**：同口径下可复现值 0.4997，引擎值高 **+0.0015（+0.3%）**。
  影响面是竞争分 `60×P/P_REF` 整体偏低约 0.3%，**量级很小**；
  但它说明这对常量**并非"同一次运行产出"**，与注释承诺不符。

> **建议（待欧文决定）**：① 先把 `scoring.py` 的注释改成实际口径（**零风险**，
> 只改注释不改数值）；② 再把 `calibrate_anchor.py` 与 `calibrate_brand_uplift.py`
> 的 REF_DP 口径统一（一个取全 83、一个取剔低证据 77），并加一条门禁断言锁住
> "注释口径 == 可复现口径"；③ `P_REF` 的 +0.0015 要么重标定一次、要么写进局限声明。

### 3.2 已同步到前端知识页

`public/sidebar.js::KB_THEORY` 的 ①② 两张卡片原文也写了"全样本中位"。
本轮已**如实修正口径表述**并**加了两条诚实披露**：
- REF_DP/P_REF 的口径实际是"剔除低证据点后 77 家"；
- `P_REF` 复现差 +0.0015（+0.3%）已记录在案、未擅自改动；
- 样本只覆盖 3 个商圈，uplift 依赖"同商圈内比较"，不能当全省通行结论；
  另有 `expand_sample.py` 做稳健性复核。

数值**一个都没动**，动的只是口径描述。
