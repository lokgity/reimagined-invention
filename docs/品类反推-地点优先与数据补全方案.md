## 一、取证：动手前我实测了什么

按项目纪律（先测真实分布再决定改哪儿），我用一次性脚本实测了三件事，跑完已删。

### 1.1 现状意图识别真值表（这是 A 的核心病根）

| 用户会说 | `_wants_shop_first` | `_is_consulting` | 当前落到 | 问题 |
|---|---|---|---|---|
| 我想在杭州滨江开店 | False | False | `no_shop` | **被反问"开什么品类"** —— 用户还没想好，被逼着先做决定 |
| 我打算在宁波天一广场那边开个店 | False | False | `no_shop` | 同上 |
| 滨江这边怎么样，适合开店吗 | False | **True** | `chat` | ❌ **想开店被判成闲聊**（真 bug 级别误判） |
| 杭州下沙适合开什么店 | True | True | `shop_first` | **追问"月租多少/面积多少"**，但用户根本没有铺子 → 死胡同 |
| 宁波鄞州万达附近想开个店，一个月租金大概多少能租到 | False | False | `no_shop` | 被问品类；用户问的"租金大概多少"**没有任何答案** |

结论：**"只有地点、没有铺子"这条路当前是断的**，而且其中一条（"滨江这边怎么样，适合开店吗"）直接掉进自由对话。

### 1.2 58 一页到底有多少货（这是 B/C 的依据）

| 探测 | 结果 |
|---|---|
| `fetch_shops('杭州', limit=80)` | 实际拿到 **64 条**；缺租金 **0** 条；缺面积 **8 条**；缺图 50 条 |
| `fetch_shops('宁波', limit=80)` | 实际拿到 **80 条**；缺租金 **0**；缺面积 **4 条** |
| PC 列表页文本 | `元/月` 出现 72 次、`㎡` 出现 424 次 |
| 翻页 `hz.58.com/shangpu/pn2/` | ✅ 可用（元/月×86、㎡×415） |
| 翻页 `pn3/` | ✅ 可用（57 / 351） |
| 筛选页 `hz.58.com/shangpu/o1/` | ✅ 可用（88 / 433） |
| 移动端 `m.58.com/hz/shangpu/` | ✅ 可用，805 行文本，**是另一套条目集合**，含「实勘铺源/安选房源/临街门面/档口摊位/商业街店铺」筛选 |

**关键发现**：现有代码 `fetch_shops(city, 10, 30, ...)` 只取 **10 条**、候选满 **6 个就 break**。
而一页有 64~88 条 —— **扩容是零成本**，不改配额、不加请求，只是把常数放大（翻页只多几次 Playwright 页面加载，不消耗高德配额）。

### 1.3 「不止 58」——我把候选数据源逐个试了一遍

| 平台 | 实测结果 |
|---|---|
| 58 同城（PC / 移动 / 翻页 / 筛选） | ✅ HTTP 200，一页 64~88 条 |
| 安居客（`m.anjuke.com` / `hz.anjuke.com`） | ❌ 「请输入验证码」，返回 720B 空壳 |
| 贝壳住宅 `hz.ke.com/shangpu/` | ❌ 404（该路径不存在） |
| 链家商业 `shangye.lianjia.com/hz/shangpu/` | ⚠️ 能开，但**只有写字楼**，且杭州未覆盖（自动回落北京） |
| 房天下 `hz.shop.fang.com/zu/`、`/shangpu/zu/hz/` | ❌ 「未找到相关页面」（默认页是"商铺出售"，出租频道已废） |
| 好租 `haozu.com` | ❌ 验证码拦截 |
| 铺专家 | ❌ 403 Forbidden |
| 乐铺 `lepu.cn` / 淘铺网 | ❌ **域名已不存在**（DNS 解析失败） |
| 百姓网 `hz.baixing.com/shangpu/` | ❌ 307 跳转到写字楼频道 |
| 中国商铺网 | ❌ 连接超时 |
| 高德 POI：`keywords=商铺出租 / 门面出租`、`types=商务住宅;商铺` | ❌ 能返回 POI（584 条），但 `biz_ext.cost` 是**空数组**、`rating` 是评分不是租金 → **高德给不了租金和面积** |

**诚实结论：除 58 之外，没有第二个可用的沿街商铺出租源。** 这不是"没试"，是"试了 10 家全封死"。
所以 D 的解法不是"再接一个平台"，而是**把 58 榨干 + 用非平台口径补全 + 严格三态标注**（见第四节）。这条结论必须写进答辩局限，不能包装成"多源数据"。

### 1.4 58 详情页能不能补面积

实测 5 个真实详情 URL（`hz.58.com/shangpu/<14位数字>x.shtml`）：

- 页面仅 3.4~4.2K 字符，**有结构化参数区**（明确抓到「楼层 1层/共1层」「转让类型」）
- 「建筑面积」用粗糙正则没命中，但参数区存在 → **需要用 CSS 选择器精确定位**（实施时验证覆盖率）
- ⚠️ 副作用提醒：详情页侧栏"猜你喜欢"里也含面积/价格文本，**粗糙正则会把别人的数字当成本店的**（我实测到 `月租: ['4.83','5000']` 其实来自推荐位）→ 取数必须限定在参数区 DOM 内

## 二、诉求 A：新增「地点优先」入口

### 2.1 新入口定义

```
place_first（地点优先）触发条件：
   有地点/区域/商圈词  ∧  有开店意向词（开店/开一家/做生意/适合开什么/怎么样）
   ∧  ¬已给品类  ∧  ¬已有具体铺子
```

与现有三条起点的关系（**互斥、不抢**）：

| 入口 | 判定 | 现状 |
|---|---|---|
| `have_shop` | 有铺子 + 有品类 → 直接评估 | 已有 |
| `shop_first` | 有铺子 + 无品类 → 四品类反推 | 已有 |
| **`place_first`** | **只有地点 + 无品类 + 无铺子 → 先推店铺再反推** | **新增** |
| `diagnose` | 已开店 + 有真实流水 → 经营诊断 | 已有 |

### 2.2 改动清单

1. **新谓词 `_wants_place_first(text)`**（`agent_graph.py`，与 `_wants_shop_first` 同级）
2. **优先级必须排在 `_is_consulting` 闸门之前**，并加进 `_wants_start_flow` 同级的"启动词"特权
   —— 否则「滨江这边怎么样，适合开店吗」继续掉进 chat（这是当前真 bug）
3. **同步 `_CONSULT_KEYWORDS` 例外表**：`适合开店`/`这边怎么样`/`能开店吗` 这类词当前会命中咨询闸门，需从闸门里豁免
4. **新 phase `place_first`**：只收「地点」（缺则一句话问全），收到即调 `search_rental_node`（扩量版）出候选
5. **选中店铺后的分岔**（改 `select_shop_node` 出口）：
   - 用户表示"还没想好做什么" → 进 `reverse_match`（**品类反推顾问真正进场**）
   - 用户已给品类/品牌 → 走现有 `collect_brand` → `collect_invest` → `analyze`
6. **`reverse_match_node` 放宽前置条件**：现在 `rent is None` 直接返回"信息不完整"，改为接受第四节的**推算租金/面积**（带三态标注）
7. **专家定义同步**（`src/experts/category_reverse.md`）：
   - `requires: [location, monthly_rent, area]` → `[location]`（rent/area 可由系统补或候选带入）
   - `tools` 增加 `fetch_shops`（`toolbox.py` 的 `VOCAB` 里**已有这个工具名**，现在只被标为"请在找铺子流程里触发"，需要放开）
   - `blurb` / `start_sentence` / `output_contract` 补第二条路径说明
   - ⚠️ `requires` 一改，`verify_experts.py` 的 frontmatter 校验会跟着跑（requires 非空则 fallback 必填）→ 需同步

### 2.3 对话示例（改造后）

系统：好的，先看看滨江现在有哪些在租的铺子。找到 14 家，已按信息完整度排序（右侧点卡片选）：

## 三、诉求 B + C：候选店铺扩量

B（推荐出租店铺）和 C（一开始定品类）**共用 `search_rental_node`**，改一处两边生效。

| 项 | 现状 | 改为 | 依据 |
|---|---|---|---|
| `fetch_shops` 抓取条数 | 10 | **60**（3 页 × ~20~88） | 一页就有 64~88 条 |
| 58 分支候选上限 | 6 | **12** | 扩容零配额 |
| 高德兜底上限 | 4 | **8** | 高德只给位置，优先级降低 |
| 本地库兜底上限 | 4 | **8** | 0 次 API |
| 候选总数上限 | 6~10 | **15** | UI 一屏可滚动 |
| 抓取面 | PC 列表页 1 页 | PC 第 1~3 页 **∪** 移动端（并集去重） | 实测两侧条目集合不同 |

**新增排序规则**（不是简单截断，避免"扩量后前 12 个全是缺字段的"）：
按 **字段完整度 → 距离区域中心** 双键排序后截断：

```
rank_key = (-完整度分数, 距区域中心距离)
完整度分数 = 有面积(1) + 有租金(1) + 有精确坐标(1) + 有图(0.5)
```

⚠️ 缺字段的候选**不丢弃，只排后面**（用户仍可点），并在卡片上如实标注。

**耗时预算**：翻 3 页 ≈ +2 次页面加载（各 3~4s），高德配额 **0 消耗**。
用已有的 `_Stage` 埋点验证总耗时；若候选检索段 > 12s，降回 2 页（这条写进验收）。

## 四、诉求 D：缺面积 / 缺租金 / 缺精确坐标怎么补

### 4.1 分层补全（每一层都有明确的诚实标签）

| 层 | 手段 | 能补什么 | 标签 |
|---|---|---|---|
| **L1 实测** | 58 列表页多页并集 | 租金（实测缺失率 0%）、面积（缺失率 ~10%） | `实测·58列表` |
| **L1 实测** | 58 **详情页**参数区（只对缺面积的候选调用，省时间） | 建筑面积、楼层、转让类型、门牌 | `实测·58详情` |
| **L1 实测** | 58 移动端并集 | 另一套条目，提高"有面积有租金"的命中率 | `实测·58移动` |
| **L1 实测** | 标题解析补面积（`35平`/`100方`/`1.6万`） | 面积（现在完全没用上） | `实测·标题解析` |
| **L2 推算** | **同区域在租挂牌参考带**（`negotiation.py::rent_benchmark` 已有，P25~P75 元/㎡/月）× 面积 | 租金**区间** | `推算·区域参考带(n=30)` |
| **L2 推算** | 品类标准面积带（`config.CATEGORY_PROFILES[cat]['area_range'/'area_ideal']` 已有） | 面积估算 | `推算·品类标准面积` |
| **L3 不可得** | 显式声明 | —— | `不可得` |

### 4.2 两处必须修的现有行为

1. **禁止静默默认 ¥8000**
   现状：`analyze_node` 里 `rent = state.get('rent') or 8000`；`select_shop_node` 还会告诉用户
   「该铺未标注租金，暂按默认 ¥8000 测算」。
   改为：租金不可得时**不出经营评分**（沿用"无月租/无面积不出分"的既有一票否决逻辑），
   并给引导："补上实际月租就能出分"。
   ⚠️ 这直接关系到 §7 的"经营评分为准"结论——**拿 8000 猜出来的分比不出分更危险**。

2. **标题价格必须做一致性校验**
   实测发现列表价会串（某卡片标题写"租金 1.6 万"，解析出 `price=1500`）。
   改为：标题解析出的租金/面积与卡片结构化字段**交叉校验**，冲突则不采（保留卡片原值）。

### 4.3 定位精度（"只有区域定位"）

- 现状：`loc` 有"街道名"就 geocode 街道，否则直接**回落区域中心**（这是"只有区域定位"的来源）
- 改进：对 `precise=False` 的候选，用 **店铺名 + 区域** 做一次高德 `place/text` 精查（比拿街道名猜准）
- 仍拿不到就保留区域级，UI 继续显示现有 ⚠️「区域级定位」标签（**不影响排序，但影响可分析性提示**）

### 4.4 取数纪律（沿用项目既有规范）

每个候选带 `来源` + `取证时间`，落盘冻结、原子写（对照 `competitor_insight.py` 的范例）；
**区分「取数失败」与「真的没有」**：`(items, meta)` 带 `ok/infocode/quota`，不许 `except: return []`。

1. **除了 58，没有第二个可用的沿街商铺源**——这是实测结论（安居客/贝壳/房天下/好租/铺专家/乐铺/淘铺/百姓网 全部封死），

3. 参考带粒度只到**行政区**、不分楼层与业态，**只能当区间不能当目标价**（这条是既有结论，不能推翻）。

5. 候选扩到 15 家后**选择成本上升**，所以必须排序，不能全列。
6. 详情页取数字必须限定在参数区 DOM 内，否则会把侧栏推荐位的数字当本店数据（已实测到该错法）。

### 10.5 回归套件抓到的两个问题（都是"表面看不出来"的那类）

**① 静默退化**：给 `band_from_samples()` 补"抓取时间"时踩了 `NameError`（该文件只在
`rent_benchmark` 里做了**函数级** `from datetime import datetime`），而调用方
`_fill_field_states` 用 `except Exception` 兜住了 → 参考带静默变 `None` →
**所有推算租金静默退化成"不可得"**。

**没有任何报错**，功能只是静默少了一块。发现它的唯一路径是回归套件里那条
「每个候选都带取证时间」。已改为模块级 import，并把这条教训写进 `negotiation.py` 注释。

**② 优先级回退**：新的 `place_first` 分支最初没加咨询闸门、且排在闸门之前，于是
「杭州开店租金什么水平？」（纯问行情）被判成"想开店" → 用户会被塞一张候选铺源列表。

抓到它的是 **`verify_flow_v2.py` 里原有的 14 条真值表**——不是新套件。
这正是"把已修的坑钉住"的价值：新功能最容易踩坏的就是旧功能的优先级。
修法：分支补 `not _is_consulting(...)`，靠 `_wants_start_flow` 里的意向词
（`适合开店`/`能开店`/`开什么店`…）区分"想开店"与"问行情"。
**新套件也已把这两条加进 must_not 组**（同一个坑不该踩两次）。

**③ 套件自身的坑**（顺带修）：`main()` 若中途抛异常，脚本会**留下上一轮的旧报告**，
看报告的人会以为刚刚通过 —— 比直接失败更危险。已改为逐节兜异常并写进报告。

### 10.6 实机验证（`live_ui_probe.py` §11，真浏览器）

⚠️ Chainlit **默认不热重载**：改完代码不重启服务，实机拿到的还是旧行为
（实测回复里赫然是改造前的"想开什么品类"）。这一步必须重启服务再跑。

服务重启后的实测结果（`_live_ui_report.txt`，rc=0 全部 PASS）：

```
说「我想在杭州滨江开店」→ 候选卡片 12 张（未反问品类，也未被判成闲聊）
                        → 网格 1 列 / 列宽 421px / 横向溢出 0
                        → 三态标签计数 == 卡片数（本批 12 张全部为实测字段）
点第 1 张 → 点后**自动**出四品类反推 4 张，含月流水/月净利/回本/起步投入
        + 口径说明（跨品类不可比）齐备
```

⚠️ 反推结果**每次不同**（候选铺源是实时抓的，点到的铺子不同结论就不同）——
两次实机分别得到「奶茶·首选·净利 11.7 万」与「甜品·首选·净利 2.8 万」，
所以文档里只记录"出了哪几项"，不把某一次的净利当固定值引用。

**顺带纠正一处想当然**：`#zl-right` 实测只有 **421px** 宽，而网格是
`repeat(auto-fill, minmax(280px, 1fr))` → 只能排 **1 列**。
原来的 `display:block` 本来也是单列，所以这次改动不是"把列表变成多列"，
而是"**面板变宽时能自动多列、窄时保持可读单列**"。
实机断言因此从"列数 ≥ 2"改成"**列宽 ≥ 240px 且不横向溢出**" —— 守的是可读性，不是列数。

### 10.7 遗留与新增代价

- **候选检索耗时 5~6s → 12.7s**（详情页补全 +6.7s）。已给硬上限
  （`RENTAL58_DETAIL_MAX=12` / `RENTAL58_DETAIL_BUDGET=7.0s`），超预算就放弃补全、
  **绝不影响列表结果**。若要更快，把 `RENTAL58_DETAIL` 置 `False` 即可关掉。
- 定位阶梯仍非 100%：无门牌、无地标、`loc` 无第二段的条目会回落区域中心
  （卡片标 `geo_state=area_level`，不假装精确）。
- 原方案第 7 条「详情页选择器覆盖率未验证」已消除：实测 8/8 目标页全部取到正文，
  6/8 取到了可用字段，**4/8 拿到了详细地址**。因详情页侧栏会串入别的铺子数字，
  面积/租金一律要求"关键词+单位"同时出现（`_DETAIL_AREA` / `_DETAIL_RENT_KW`），
  且**只补不覆盖**。
