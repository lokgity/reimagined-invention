## 1. 诉求①：品类不该在前期问 —— 根因有三条，其中两条现在仍然存在

### 1.1 先说已经修好的那条（你 02:38 那次是真的踩到了）

`# 早上好，BOSS` 页面左侧历史会话里能看到三条「我想在杭州滨江开店」（02:38 / 02:42 / 02:42）。**02:38 那次跑的是改造前的进程**——Chainlit 不热重载，我 02:41 才重启服务，所以那次确实是「问品类」。02:42 之后的两次已经是新逻辑（地点优先 → 候选铺源 → 选中后四品类反推），实机全链路已验过。

也就是说：**这条不算"没做"，但你后来遇到的很可能不是它，而是下面两条——它们现在仍然会把品类问到用户脸上。**

### 1.2 仍然存在的路径 A：「找」字开头的话会把地点优先顶掉

`agent_graph.py:520`（`_wants_place_first` 内）：

```python
if _wants_find(t) or _wants_restart(t):   # "帮我找铺子"走 A 流程（先问品类）
    return False
```

`_wants_find`（`:284`）命中词包括：`帮我找 / 帮我查 / 推荐 / 帮我看看 / 找商铺 / 找店 / 找铺 / 哪里开 / 哪个位置 / 有哪些店`。

于是：「帮我找杭州滨江的铺子」「推荐个开店的地方」「哪个位置适合开店」→ 全都被推进 A 流程 → `collect_info_node`（`:1094`）执行：

```python
if not state.get('category'):
    missing.append('想开什么品类？（奶茶/甜品/早餐/便利店）')
```

**这就是你被问品类的主路径。**

### 1.3 仍然存在的路径 B（更刺眼）：把铺子三件套给全了，还是问品类

`_has_specific_shop`（`:271`）看到「路/街 + 门牌号」或「大厦/铺位/门面/栋/幢」就判定"用户已有具体铺子" → `phase = have_shop` → 而 `have_shop` 缺品类时同样追问品类（`:1119`）。

举个真实输入：**「杭州滨江江陵路 88 号，30 平，月租 8000」**
→ 判定"已有具体铺子" ✅ 租金 ✅ 面积 ✅ 品类 ✗ → **系统问你"想开什么品类？"**

而按产品自己的逻辑，这恰恰是**反推品类最理想的输入**（有铺、有租金、有面积、没想好做什么 = `shop_first`）。它之所以没走 shop_first，是因为 `_wants_shop_first`（`:432`）要求句子里有"有个铺子"这类措辞，或者"不知道做什么"这类话——**你只是把数据报出来，没这么说**。

### 1.4 改法（建议）

**统一口径：品类缺失时永不主动索要，改为"先铺子/先反推"。**

| 场景 | 现在 | 改后 |
|---|---|---|
| 「我想在滨江开店」（无铺、无品类） | ✅ 已正确：先推铺源 | 不变 |
| 「帮我找滨江的铺子」「推荐个开店的地方」（无铺、无品类） | ❌ 问品类 | 先推铺源（把 `_wants_find` 从排除名单里去掉，**仅当同时给了品类时才走 A 流程**） |
| 「滨江江陵路88号 30平 月租8000」（有铺、无品类） | ❌ 问品类 | 直接四品类反推（`have_shop` 缺品类 + 铺子数据够 → 转 `shop_first`） |
| 「我想开奶茶店」（有品类、无铺） | 问地区（合理） | 不变 |
| 「有铺子 杭州滨江 月租8000 30平，做什么好」 | ✅ 已正确 | 不变 |

**A 流程（先定品类 → 找铺）只保留一种触发条件：用户自己说了品类。** 这与"品类反推员"的产品定位一致——反推是他的本职。

**代价与风险**：`_wants_find` 的 `推荐/帮我看看/哪里开` 是很宽的词，放开后有误判风险（比如「推荐几本书」）。所以我会：①用"必须同时出现地点或经营词"做二次约束；②把这三条写进 `verify_place_first.py` 的真值表（must/must_not 两组），并保留 `verify_flow_v2.py` 原有的"纯问行情不得被当成开店"断言防回退。

## 4. 诉求④：前期投入的口径 + 加盟费提示 + 下限校验

### 4.1 先回答你的问题：「前期投入」到底含不含加盟费？

**现在的代码是自相矛盾的**，这是你困惑的真正来源：

| 位置 | 口径 |
|---|---|
| `engine/utilities.py:344-352` | 优先级 = **用户输入 > 品牌参考 > 通用估算**；`FRANCHISE_INFO.invest_ref` 的口径在 `brands.py:272` 明确写着「**含加盟费/保证金/设备/装修，不含房租押金**」 |
| `ask_investment_message`（`agent_graph.py:727`） | 问用户时写的是「含**装修+设备+首批物料+转让**等」——**没提加盟费** |
| `_default_investment`（`:717`） | 面积×4000 + 3 万，**不含加盟费** |
| `state.py:24` 注释 | 「含装修+设备+首批物料等」，也没提加盟费 |

所以：**品牌参考口径含加盟费，用户填写口径没写清、默认估算又不含** —— 用户填 12 万去开蜜雪（官方口径 37 万起）时，系统会照算，两边不可比。

**建议定稿口径：**

> **前期投入成本 = 加盟费 + 保证金 + 设备 + 装修 + 首批物料 + 转让费，不含房租押金**（与 `invest_ref` 一致）。
> 房租押金单列，因为它不进 `月成本合计` 也不进摊销；而加盟费/装修/设备要摊 36 个月。

**但「算没算、是不是双算」这件事，我实跑了一遍引擎来回答你**（脚本 `_t_fee.py` 直接调 `estimate_profit`，蜜雪冰城为例，输出留档 `_t_fee_out.txt`）—— **结论是分路径的**：

| 路径 | 加盟费 1.1 万/年 的落点 | 结论 |
|---|---|---|
| **A / B：用户自报投入** | 只在**月度成本**里出现一次：`月品牌费 1,317 = 加盟费 917/月 + 管理费 400/月`（按年费 15,800 拆 12 个月）。至于**投入基数含不含加盟费，完全取决于用户自己填没填** | **算了一次，不漏也不双算** |
| **C：用户不报投入 → 走品牌参考 `invest_ref` = 37 万** | `invest_ref` 口径**已含加盟费** → 摊销里含 `306/月（= 11,000 ÷ 36）`；**同时**月品牌费又收 `917/月` | **同一笔 11,000 元/年 被算了两遍**：一遍当一次性投入摊销，一遍当月费 |

实测数字（蜜雪冰城）：

| 场景 | 前期投入 | 月摊销 | 月成本合计 | 月净利 | 回本周期 |
|---|---|---|---|---|---|
| A 自报 12 万（**没**把加盟费填进投入） | 120,000 | 3,333 | 87,672 | 32,328 | **3.4 月** |
| B 自报 13.1 万（= 12 万 + 加盟费 1.1 万） | 131,000 | 3,639 | — | 32,022 | **3.7 月** |
| C 不报 → 品牌参考 37 万 | 370,000 | 10,278 | 94,616 | 25,384 | **10.4 月** |

**所以回答分两句：**

1. **A/B 路径：加盟费没被漏掉**（它以「年品牌费」的身份进了月成本），也没有双算。**但** —— 如果你按提示语的默认理解填了「12 万（不含加盟费）」，那**投入基数里就真的少了这 1.1 万**，代价是回本从 3.7 月被压到 3.4 月，即**回本被低估 8.1%**（净利差 306 = 11,000 ÷ 36）。
2. **C 路径：存在真正的双算** —— 摊销与月品牌费同源于同一笔年费。

> ⚠️ **更正**：上一版本文档在这里写过「不存在加盟费既进摊销又进月成本的双算问题 —— 这点已经是对的，不用改」。**这句话是错的**，已被上面的实测证伪，特此更正。

**C 路径的双算怎么处理 —— ✅ 已定：不改（2026-09-17 欧文决策）。**

## 5. 诉求⑤：欢迎语美化 —— ✅ 已定案并落地（2026-09-17，欧文选「定位针」）

**现状**：`早上好，BOSS` 本来就是金色渐变的艺术字（衬线展示字体 + 主题自适应：深色金渐变 / 浅色墨绿→金），在 `sidebar.js` 的 h1 规则里。~~所以这条需求真正缺的只是**花纹**。~~ ⚠️ **这句判断后来被欧文推翻**（「渐变还是太不明显」）—— 渐变确实写了，但**看不出**，见下面的返工记录。

**渐变返工（2026-09-17 追加，起因：欧文「这几个字的渐变还是太不明显，改明显一点」）**

查出来是三条原因叠加，**缺一条都还会犯**：

1. **背景压根没铺在文字上。** h1 是**块级**元素，默认撑满整行（实机量到 ~750px），而「早上好，BOSS」只占 ~260px。渐变按整行铺，文字只截到中间约 1/3 的色阶 —— 几色被压成一片，看着就是单色。**这是主因**，也是纯靠"调配色"永远修不好的那一半。
2. **色标全落在同一金色系内**，色相差极小，所以「明显」只能靠**明度**落差撑；旧版亮部 ~86% → 暗部 ~59%，感知亮度极差只有 **≈26**，本就偏弱。
3. **`text-shadow` 会从字形内部透出来。** 字身是 `-webkit-text-fill-color:transparent`，阴影画在字形下方却能从透明的字身里透出来，把渐变糊平。（改用 `filter:drop-shadow()`：作用在渲染结果上、不穿字身 —— 光晕留住了，字面色不脏。）

修法（都落在 h1 那两条主题规则里）：

- `display:block; width:fit-content; max-width:100%` —— 盒子收缩到「花纹 + 文字」的内容宽，色阶不再被摊薄；
- `background-size:calc(100% - 96px) 100%; background-position:48px 50%; background-repeat:no-repeat` —— 再把背景**只铺在文字区**（左右各 48px = 花纹 34px + 间距 14px）。**这两个数与花纹尺寸是联动的**：改花纹大小必须同步改，否则渐变会缩到花纹底下或截断字尾（`verify_ui.py` §8 有断言把这个联动钉死，改花纹尺寸会直接 FAIL）；
- 4 色标、`100deg`，暗部压到 `#c9761a`（深色）/ `#8a7d2c`（浅色），感知亮度极差抬到 **46.9 / 51.9**（断言阈值 ≥40，旧值 26 会被拦住）。

**验收方式同步升级**：静态断言只能证明「色标写对了、`fit-content` 写了」，那是**必要条件不是充分条件**。「到底看不看得出」是**视觉**问题，只有量像素才算数。实机新增：截 h1 元素图 → 跳过左右花纹 → 沿 x 逐列取文字像素 → 断言**明度极差 ≥ 28**，并把左→右的明度走势（10 等分）打进报告存档。这是本项目第一次用像素采样验收观感，理由与「`scroller()` 空转只有实机能发现」同源：**断言能证几何，证不了观感**。

⚠️ 分离文字像素必须用**色相**判据（金色 `R-B ≈ 175`、冷墨绿背景 `R-B ≈ -28`），**不能用"亮度高于背景"**：文字带 drop-shadow 光晕，光晕把背景抬到 ~59，而渐变暗部文字本身只有 ~52，两者挨得极近 —— 按亮度筛列会把**最暗那几列**（恰恰是"到底明不明显"的证据）当成背景扔掉，极差被系统性低估（第一版实测 25.4 / 设计值 ~47，就是这么来的）。这条教训对任何"文字带光晕"的观感采样都适用。

**实测（像素采样，两主题都跑了）**：

| 主题 | 文字明度沿 x 走势（左→右 10 等分） | 极差 | 形状对应 |
|---|---|---|---|
| 深色（应用默认） | `90 86 79 72 57 60 65 72 79 86 85` | **60.3** | **U 形**（亮→暗→亮），与色标 0/26/56/100% 的金属光泽设计一致 |
| 浅色 | `21 25 24 27 29 39 43 46 50 54 57` | **50.3** | **单调递增**，与深墨绿→青绿→橄榄金→金的色标设计一致 |

⚠️ 深色的 60.3 略高于色标设计值 47，来自**两个方向相反的偏差**：暗端混入少量**抗锯齿像素**（最低被拉到 32，比纯色 52 更暗 → 抬高极差），亮端的**近白金**像素因 `R-B` 太小（≈15，与光晕背景的 22 不可分）被判据排除（又压低极差）。量级可信、但不是精确色值 —— 更强的证据是**走势曲线的形状**与色标设计对得上。浅色的 50.3 则与设计值 50 基本吻合（浅色文字比底暗，用"每列最暗像素 + 剔除背景列"采样，无光晕干扰）。

**花纹定案**：我先渲了三版对照稿给欧文看（按「品类 / 职能 / 气质」三条轴各出一版：**茶芽 / 定位针 / 云纹卷草**），**欧文选「定位针」**（渲染稿里的"方案 B"）。

> ⚠️ 本节早前草案里也写过一组 A/B/C（地图钉+涟漪 / 奶茶杯+星点 / 叶脉+刻度线）。那组**没渲成稿就被取代了**，别拿它去对代码 —— 以渲染稿的三个为准。

**实现**（`sidebar.js`）：

- 花纹 = 内联 SVG 走 **data-URI**，贴在 h1 的 `::before` / `::after` 上（严格镜像成对，左右各一枚）。
- **为什么不把 `<svg>` 塞进 welcome 文案**：Chainlit 的 markdown 会把原始 HTML sanitize 掉，塞进去只会露成一堆标签。纯 CSS 另外白捡两个好处 —— 历史会话回放同一条欢迎语时花纹自动生效、后端文案一个字都不用动。
- **颜色走 `--zl-pin` 自定义属性**（data-URI 内部写不了 `var()`），所以深/浅两套各生成一份 SVG，分别挂在既有那两条 h1 主题规则上。**浅色覆盖规则必须排在深色之后**（两条同权重，只靠源码顺序取胜）。
- **34px 是配 44px 标题的固定值，且故意不进 `--zl-fs` 缩放层** —— 标题字号本身不在缩放层里，花纹进去了就会两边不同步。将来谁给 h1 加缩放，必须同时把这两条改成 `calc()`。
- 伪元素显式 `background-clip:border-box`，防父级 `-webkit-background-clip:text` 把花纹裁没。

**验收**：

- 静态（`verify_ui.py` §8）：覆盖「全 src 只有欢迎语一处一级标题」（h1 选择器是全局的，将来谁再加一个一级标题，就会莫名长出定位针）、花纹 data-URI、深浅两份、左右留白、尺寸不进缩放层，以及**渐变可读性**（`width:fit-content`、背景扣掉 96px、明度落差 ≥30、已弃用 `text-shadow`、留白与花纹几何的**联动**）。
- 实机（`live_ui_probe.py`）：必须用 `getComputedStyle(el, '::before')` 读伪元素（**伪元素不在 DOM 里，`querySelector` 查不到**），断言背景确实是 `data:image/svg`、左右同一图案、两侧留白各归一边、尺寸非零、**h1 高度仍是一行量级（不跳版）**；再加**观感两条** —— h1 盒子已收缩到内容宽（`h1W ≤ 460`，撑满整行时约 750）、沿 x 采样文字像素的**明度极差 ≥ 28**（用色相判据分离文字，见上）。截图 `_ui_shots/10_welcome_motif.png`。
- 实机 · **浅色主题**（`src/analysis/light_theme_probe.py`，本轮新建）：项目铁律是「改样式必须**两主题都验**」，而 `live_ui_probe.py` 固定跑应用默认的深色 —— 浅色那一面过去没人盯（正是「硬编码亮色在浅底看不清」那类坑的温床）。本脚本切掉 `html.dark` 后复验同一组指标（浅色下文字比背景暗，改用「每列最暗像素 + 剔除背景列」采样）。同属实机层、**不进**离线门禁。截图 `_ui_shots/11_welcome_motif_light.png`。
