# 专家系统方案评估：要不要做、怎么做、做到什么程度

> 日期：2026-09-15（正文为当时的评估与方案；**落地结果见第九节**）
> 问题：是否给「址南针」做一个**专家系统**——每个专家对应一个 skill、让用户选择？
> 结论先行：**建议做，但要做成"专家层"，不要做成"每个专家一条独立流水线"。**
> 依据：现有 6 个专家角色**已经以节点形式存在于同一个 LangGraph 里**，
> 缺的不是能力，而是**可见性 + 人设 + 边界**。这是一次"重新组织与暴露"，不是"新建功能"。
>
> ⚠️ **读法提示**：下面第一～八节是 2026-09-15 的**评估与候选方案**（保留决策过程）；
> 其中"首屏专家卡片"这个入口形态**已于 2026-09-16 晚被用户否掉并替换**
> （改为「输入框上方专家条 + 左栏专家系统卡片页 + `/expert`」）。
> **要看最终做了什么，直接跳第九节**；要看"为什么否掉"，看第九节的三入口对照表。

## 一、先看清：你想做的专家，其实已经都在了

| 你想要的"专家" | 现在在哪 | 状态 |
|---|---|---|
| 选址顾问（综合解读） | `interpret_node` + `rule_based_interpret` | ✅ 已有 |
| 租金谈判教练 | `negotiate_node` + `engine/negotiation.py` | ✅ 已有 |
| 竞品分析师 | `competitor_node` + `engine/competitor_insight.py` | ✅ 已有 |
| 加盟顾问 | `collect_brand_node` + `engine/brands.py` 加盟政策 | ✅ 已有 |
| 门头审核员 | `vision.py` + `scoring.apply_storefront` | ✅ 已有 |
| 流程向导（默认） | `classify_node` / `collect_*` / `search_rental_node` | ✅ 已有 |

所以"做专家系统"真正要交付的是三样东西：

1. **用户看得见的选择入口**（Chainlit 侧栏/Settings 的下拉或专家卡片）
2. **每个专家一个明确人设**（system prompt 的 persona 段）
3. **每个专家一条明确边界**（能用哪些工具、缺什么前提、输出什么结构）

**这三点加起来约等于一次"界面 + 提示词组织"的工作量，不是一次架构重建。**

---

## 二、核心风险：一个做错就会翻车的设计

> ⚠️ **最大的坑：把"专家"做成独立入口 / 独立会话。**

现在的链路是一个**闭环状态机**：

```
选铺 → score_site → score_result（评分/流水/成本/回本/租金临界点）
                        ↓
        解读 / 谈判 / 竞品 / 门头 全部读同一份 score_result
```

- 谈判教练的"承受力上限"来自 `score_result.rent_limits`
- 竞品分析的"客单价现实校验"依赖 `score_result.brand` 与坐标
- 解读必须引用 `score_result.evidence`

**一旦让用户"进谈判专家 → 新会话"，score_result 就没了**，
谈判专家立刻只会说空话（"多比较几家""压价 5%"）——这正是它现在被刻意避免的东西。

### 结论

| 做法 | 判定 |
|---|---|
| 单一会话 + 共享 state，专家只切**视角** | ✅ 推荐 |
| 每个专家独立会话 / 独立 Agent | ❌ 会拆掉闭环，谈判与竞品立刻退化 |
| 每个专家一套完整流程重写 | ❌ 重复实现状态机，维护成本翻倍 |

## 三、推荐架构："专家层"，不是"多 Agent"

```
                    ┌──────────────────────────────────┐
                    │   共享会话状态 AgentState          │
   用户选择专家 ───▶ │   category / brand / score_result │
   （或自动路由）     │   rent / area / context / hooks   │
                    └───────────────┬──────────────────┘
                                    │  所有专家读同一份
        ┌───────────────┬───────────┼───────────┬───────────────┐
        ▼               ▼           ▼           ▼               ▼
   选址顾问        租金谈判      竞品分析     加盟顾问        门头审核
   persona A       persona B    persona C    persona D      persona E
   工具:全部       工具:negot.  工具:竞品    工具:brands    工具:vision
   输出:解读结构   输出:筹码+话术 输出:格局   输出:政策参考   输出:9 字段
```

### 3.1 专家定义放哪 —— "每个专家 = 一个 skill 文件"

这一层完全可以用文件承载，新增专家不用改代码：

```
src/experts/
  registry.py            # 扫描 + 加载 + 校验
  site_advisor.md        # YAML frontmatter + prompt 正文
  rent_negotiator.md
  competitor_analyst.md
  franchise_advisor.md
  storefront_auditor.md
```

```markdown
---
id: rent_negotiator
name: 租金谈判教练
icon: handshake
requires: [score_result]        # 缺前提时的兜底话术
tools: [negotiation_brief, kb_retrieve]   # 工具白名单
output_contract: 先结论 → 天花板≠开价 → 差额锚 → 3-5 条话术
---
你是一位租金谈判教练。铁律见下方"公共铁律"，你的增量职责是……
```

好处：
- **"skill"在架构上真的成立**，不是换个人设的幌子
- 加专家 = 加一个 md 文件（答辩时很好讲）
- `tools` / `requires` / `output_contract` 都是**可断言**的字段

### 3.2 关键工程细节：组合式 prompt，不要复制粘贴

**这是最容易做砸的地方。** `interpret_node` 那段 system prompt 里有 9 条强约束
（必须引用证据、必须把三档情景与口径区间**分开讲**、veto 优先级高于总分、
禁止编造数字……）。如果 6 个专家各抄一份：

- 改一次铁律要改 6 处 → 必然漏 → 6 个专家行为不一致
- 测试没法写（每个专家各测一遍铁律？）

**正确做法**：

```
最终 prompt = 公共铁律（1 份，所有专家继承）
            + 专家 persona（各自增量）
            + 该专家允许的工具产生的证据包
```

这样"数字不许编""必须报口径""必须转达局限声明"这些铁律只有一处定义，
专家文件只写**自己的增量职责**。

### 3.3 让"专家"有可验证差异（否则会被一眼看穿）

如果 6 个专家只是 6 段不同的 system prompt，评委会问：
**"这和聊天时换个人设有什么区别？"**

要给每个专家至少**两个硬差异**：

| 差异维度 | 说明 | 可断言性 |
|---|---|---|
| `tools` 白名单 | 谈判专家**不允许**调 vision；门头审核**不允许**产流水 | 可测（调用被拒） |
| `requires` 前提 | 缺 `score_result` 时谈判专家必须**明说给不出**，不硬编 | 可测（断言输出含"给不出"） |
| `output_contract` | 竞品专家必须输出 HHI/连锁占比；门头专家必须输出 9 字段 | 可测（字段存在性） |
| 兜底路径 | 各专家的 LLM 失败降级产物不同（规则解读 / 纯筹码 / 离线模板） | 可测（已在 `verify_degrade_fallback.py` 覆盖） |

## 四、与 WorkBuddy 专家中心的关系（顺带说清）

WorkBuddy 本身的"专家中心"就是**这个模式的产品化**：用户从侧栏选专家，
每个专家有自己的方法论与工作流。区别是：

- WorkBuddy 的专家是**通用**的（换行业换任务都能用）
- 你的专家是**垂直**的（只服务商铺选址），而且**共享同一份量化引擎结果**

所以你可以借它的**交互范式**（选专家 → 进入该专家的对话视角），
但**不能借它的"专家是独立会话"这层**——那正是第三节说的坑。

> 如果你也想把项目本身打包成一个可被复用的专家包（给别的 Agent 用），
> 那是另一件事：需要按专家包规范写 `SKILL.md` + 方法论 + 工作流。
> 但这对当前答辩目标（把选址系统讲清楚）收益不高，优先级应排在专家层之后。

## 六、如果不做 / 做轻量版

**不做**也可以是合理选择：

- 现在**自动路由已经能用**（`_wants_negotiate` / `_wants_competitor` 关键词路由），
  用户说"租金怎么谈"就会进谈判节点。功能上不缺东西。
- 专家系统的**收益主要是"可发现性"与"答辩叙事"**，不是新能力。

**轻量版**（推荐给时间紧的情况）：**只做"专家快捷入口卡"，零架构改动。**

在欢迎语下方给 5 张卡片（选址顾问 / 租金谈判 / 竞品分析 / 加盟政策 / 门头审核），
点击 = 预填一句指令发给现有流程。用户感知几乎等同于专家选择，
但不用动 state、不用拆 prompt。

> 这个轻量版在答辩里同样能讲"多专家协作"，而且**风险为零**——
> 因为它不改变任何既有链路，只是给现有节点加了几个入口按钮。

## 七、建议与决策点

**我的建议：做 P0+P1。** 理由：

1. **成本低**：6 个专家已经存在，做的是暴露与组织，不是新开发。
2. **答辩价值高**：能讲清"多角色协作 + 共享量化底座 + 每个角色有工具边界与前提依赖"。
3. **风险可控**：只要坚持"单会话 + 共享 state + 组合式 prompt"，不会拆掉闭环。

**需要你拍板的三个点**：

| # | 决策点 | 备选 |
|---|---|---|
| 1 | 专家是"显式选择"还是"自动路由"？ | 我建议**混合**：默认自动（现有行为不变），侧栏可手动锁定专家 |
| 2 | 专家数量 | 我建议**5 个**（选址/谈判/竞品/加盟/门头）；流程向导不单列为专家，它是默认态 |
| 3 | 是否要让专家"锁定后禁止越界" | 我建议**不禁止**，只做**提示**——用户锁定谈判专家却问竞品，硬拦会让人困惑；提示"这个问题更适合竞品分析师，要切过去吗？"体验更好 |

## 八、诚实标注（方案自身的局限）

1. 本文的**工作量判断是量级估计**，未做实际工时统计。
2. **P1 的 prompt 拆分有回归风险**：现有 9 条铁律被 4 个节点共用且措辞高度定制，
   拆成"公共铁律 + 增量"时若语义漂移，可能让既有解读质量下降。
   建议拆分时**保持 P0 与 P1 分两次提交**，中间跑一次全量回归对比。
3. **专家级断言覆盖的是结构，不是语气**：能保证"谈判专家不产流水数字"，
   不能保证"话说得像人话"。后者仍需人工抽查。

kb=**政策语料与分区检索一起补**；
入口=**首屏卡片 + `/expert` 随时切换** →
**2026-09-16 晚按用户反馈改为「输入框上方专家条 + 左栏专家系统卡片页 + `/expert`」三入口**

**新增的真问题（都已修，详见 `src/experts/README.md` §九）**：
① `_common.md` 铁律编号重复（11 写成第二个 10）→ 加**编号连续性哨兵**；
② 已开店用户被"我有个店"抢进品类反推 → 靠**判定顺序** + 6 条正反例锁死；
③ 「自由对话」气泡**永久可见**（不是"闪一下"）——根因是 5 处白名单**全都不含**这两条指令，
`hideTarget` 从未被设置 → 三条隐藏规则全部落空；把"专家"一起加进去，否则修完 ① 又会冒同一类；
④ `##专家:xxx##` 解析出的是 `xxx##`（`split(':',1)` 没削尾巴）→ 潜伏 bug，
此前无前端调用者所以没暴露，已 `.rstrip('#')` 并加断言。

**仍存在的边界（诚实标注）**：
- 九位专家的话术质量**未做质量抽检**，`assertions` 只覆盖结构；
- §8 的 UI 哨兵只断言"接线在"，**不能证明 JS 逻辑正确**（浮层是否会误遮、面板定位是否漂移，仍需手测）；
- 4 个政策方向（健康证/注册主体/所得税/消防）语料未覆盖，系统明说"暂未收录"；
- 经营测算专家的**成本率仍是假设区间**（与选址侧共用），用户有真实账目时应替换为实测值。
