# 经营测算口径与「已开店」诊断

> 日期：2026-09-15
> 触发：专家体系新增「经营测算专家」（服务**已开店**店主），必须先定死两个口径
> ——**毛利率算不算外卖抽成**、**流水从哪来**——否则这个专家说出的每个数字都站不住。
> 涉及文件：`src/engine/utilities.py`（毛利率）、`src/engine/store_diagnosis.py`（新增）、
> `src/agent/knowledge.py`（营销语料）、`src/analysis/verify_store_diagnosis.py`（新增回归）

---

## 一、要回答的两个问题

| # | 问题 | 为什么必须先定 |
|---|---|---|
| 1 | 外卖抽成算不算进成本、算不算进毛利率？ | 奶茶外卖占比 35%、平台抽成 22% → 抽成吃掉流水 **7.7%**。算与不算，"毛利率"这一个词能差出 7.7 个百分点，对外说就没法统一 |
| 2 | 已开店的流水从哪来？ | 选址侧是**模型估**（Huff 引力模型，含未标定的价格-单量弹性）。已开店的人**知道自己真实流水**——再用模型估就是拿假设覆盖事实 |

## 二、口径 1：外卖抽成 **不进**毛利率，但必须并列单列

### 2.1 决定

```
毛利率        = (月流水 − 月物料 − 月损耗) / 月流水      ← 产品口径，即 COGS 口径
外卖抽成占流水比 = 外卖占比 × 平台佣金率  = 35% × 22% = 7.7%
扣渠道后毛利率  = 毛利率 − 外卖抽成占流水比
```

三个数**并列输出**（`estimate_profit` 的 `毛利率` / `外卖抽成占流水比` / `扣渠道后毛利率`）。

### 2.2 理由（三条，按重要性排序）

1. **毛利率是行业通用口径，不能自创。** 餐饮业"毛利率"默认指 **营业额 − 食材成本**。
   若把平台抽成算进 COGS，本系统报出的毛利率就与所有人（加盟商面试、银行贷款、
   同行对比、招股书）的口径不一致，**无法与外部数据对照**——而本项目最值钱的资产
   恰恰是"能和公开披露对照"（见 `brand_store_metrics.csv`）。
2. **抽成的性质是"渠道 / 销售费用"，不是"产品成本"。** 同一杯奶茶，堂食卖出去和
   外卖卖出去，物料成本完全相同；差别在**通过什么渠道卖**。把它塞进 COGS 会掩盖
   一个可行动的结构性杠杆：**外卖占比本身就是成本变量**。
3. **混进毛利率会让"该调什么"变得看不见。** 并列之后，店主一眼能看出两件事：
   产品本身还有 65% 空间（→ 供应链还有得谈）；但渠道又拿走 7.7%（→ 降外卖占比
   与压抽成档位是独立动作）。合成一个数就两个都看不见。

### 2.3 落地形态

- 引擎输出常量 `GROSS_MARGIN_CALIBER = '产品口径（流水 − 物料 − 损耗）；不含外卖抽成/人工/租金'`，
  随结果一起返回，**上游必须原样转达**，避免二手解释走样。
- 回归断言：毛利率可复算（`= 1 −(物料+损耗)/流水`）、扣渠道后毛利率 `= 毛利率 − 7.7%`、
  且**毛利率不随流水规模变化**（它是率，不是额）——最后这条能挡住"把额当率"的回归。

### 2.4 已知的口径陷阱（勿踩）

- ⚠️ `utilities` 里另有 key `外卖抽成率`，它是**平台佣金率 22%**，**不是**"占流水的比例"。
  占流水比例叫 `外卖抽成占流水比`（7.7%）。两者名字接近、含义差 3 倍，已在 docstring 标注。
- ⚠️ `月固定成本` 这个 key 的名与值不符，见本文 §五。

## 三、口径 2：已开店流水由 **用户自报**，模型不估

### 3.1 与选址测算的分界

| | 选址测算 `score_site` | 已开店诊断 `diagnose_existing_store` |
|---|---|---|
| 流水 | **模型估**（Huff，含"价格-单量弹性未标定"的不确定性） | **用户自报**，不估 |
| 位置 | 待定，需算位置分 | 已定，只做经营拆解 |
| 回答 | 能不能开、租金上限多少 | 现在哪里不对、还有多少缓冲 |
| 不确定性来源 | 模型假设 | **只有用户自报数的准确度** |

**这条设计带来一个重要好处**：选址侧那个"未标定的价格-单量弹性"在已开店场景里
**根本不存在**——流水是事实，不是推断。所以诊断结论的不确定性远小于选址结论。

### 3.2 输出结构

输入：`品类 / 月流水（或 日单量×每单金额）/ 月租金 / 面积 / 城市 / 人数 / 品牌`

输出：成本拆解（11 项）· 三种毛利口径 · 净利率 · **安全边际** · **租金余量** ·
品牌公开基准对标 · 诊断文本 · 局限声明。

### 3.3 安全边际用引擎自己解，不引外部经验阈值

```
变动成本率 v = 物料占比 + 损耗率 + 外卖占比×抽成率 + 场地附加费率 + 税负率
固定成本   F = 租金 + 人工 + 水电 + 摊销 + 品牌费 + 杂费
盈亏平衡月流水 = F / (1 − v)
安全边际率 = (实际流水 − 盈亏平衡流水) / 实际流水
盈亏平衡月租 = 实际流水×(1−v) − (F − 租金)
```

**为什么不用"行业经验说安全边际要 ≥20%"这类阈值**：本项目的数据资产不支持编一个
阈值出来。改用自洽检验——把流水代回模型，净利必须 ≈0；且自解的 `盈亏平衡月租`
必须与 `scoring.solve_rent_limits` 的**独立二分算法**吻合（同一模型、两条算法）。
实测两者差 **¥13**（自解 ¥13,663 / 二分 ¥13,650），已固化为回归断言。

## 四、品牌对标：只认公开披露，没有就不编

基准来自 `src/engine/brand_store_metrics.csv`（招股书/年报口径），换算式
`基准月流水 = 单店日均 GMV × 30`。

| 品牌 | 基准月流水 | 期间 | 能否给基准 |
|---|---|---|---|
| 蜜雪冰城 | ¥125,532 | 2024 年前 9 个月 | ✅ |
| 古茗 | ¥195,000 | 2024 全年 | ✅ |
| 沪上阿姨 | ¥114,990 | 2024 全年 | ✅ |
| 霸王茶姬 | ¥504,840 | 2024 全年 | ✅ |
| 茶百道 | — | 未披露单店 GMV | ❌ **不给** |
| 奈雪的茶 | — | GMV 是区间字符串 `6800~8900` | ❌ **不给** |
| 喜茶 | — | 未收录 | ❌ **不给** |

- **不给基准的三条都进了回归**：茶百道（缺列）、奈雪（区间串 → 不猜中位数）、
  喜茶（未收录）。**不猜中位数**是本项目"不编数据"铁律的直接落地。
- 对标结论必须带出**披露期间**与**来源**：品牌平均 ≠ 同商圈同面积可比店，
  只能判断量级，**不能当业绩考核线**。该限制随结果一起返回，写进 `局限`。

## 五、顺带发现并修掉的命名陷阱：`月固定成本` 实际是**总成本**

### 5.1 问题

`utilities.estimate_profit` 的 `fixed_cost` 变量累加的是**全部成本**（含物料、损耗、
外卖抽成、场地附加、税——这些都是随流水变动的项），键名却写作 **`月固定成本`**，
并被 UI 明细表、PDF 报表、规则解读文案直接展示给用户。

实测（宁波 30㎡ 奶茶 / 自报流水 8 万 / 蜜雪）：

| | 金额 |
|---|---|
| 真固定成本（租金+人工+水电+摊销+品牌费+杂费） | **¥37,777** |
| 该键实际值（= 总成本 = 流水 − 净利） | **¥78,336** |
| 倍差 | **2.07×** |

把总成本标成"固定成本"展示，会让店主低估可变成本、误判盈亏平衡点。

### 5.2 处置

- 变量 `fixed_cost` → **`total_cost`**；规范输出键 → **`月成本合计`**。
- `月固定成本` **保留为兼容别名**（值同总成本），仅为让历史 `analyses.json` 仍可读，
  已在 docstring 标"已废弃"。
- 三处用户可见标签改为 `月成本合计`：`app_chainlit.py`（明细表 + 指标清单）、
  `report_pdf.py`、`agent.py`（规则解读）。
- `store_diagnosis` 输出里**两个都给且并列**：`月固定成本`（真固定，新算）
  与 `月成本合计`（总成本），并加注释说明"同名不同义"。
- 回归哨兵：断言 `月成本合计 == 11 项分项之和 == 流水 − 净利`，且
  **`月成本合计 > 月固定成本 × 1.3`**（防有人再把两者当成同一个数）。

## 六、知识库缺口②：新增「营销与运营」语料（方案 B）

已开店诊断要回答"营销怎么调"，而此前 6 类语料里**没有任何营销/运营内容**，
建议只能靠 LLM 通用知识、无本地锚。

新增 6 条（`KNOWLEDGE_BASE` 24 → 30），**逐条带 `source` 字段**：

| 条目标题 | 来源类型 |
|---|---|
| 外卖渠道费用构成 | 平台商家规则页（技术服务费 + 履约服务费） |
| 堂食与外卖的利润差异 | 本系统成本模型推导 |
| 会员与私域复购 | 平台官方商家运营指南 |
| 平台评分与门店曝光 | 平台官方商家规则与运营指南 |
| 客单价与出杯结构 | 品牌公开披露（`brand_store_metrics.csv`） |
| 时段结构与淡旺季 | 行业通用认知（**明确标注无可引用系数**） |

**收录标准（与"不编数据"铁律一致）**：只写**可核验的机制性事实**（费用构成、
链路、可操作项），**不写没有出处的精确统计数字**。凡本系统没有实测支撑的，
在正文里直说"无可引用系数，任何具体百分比都不应由此条推出"。

### 6.1 连带的三处工程改动

1. **`source` 进注入文本**：`build_context` 现在会把来源附在正文后
   （`…（来源：…）`），LLM 才能归因——否则"有来源"只是躺在数据里的装饰。
   无 `source` 的老条目格式不变。
2. **`min_score` 必须重新标定**：语料 24 → 30 改变 IDF，进而改变所有余弦相似度。
   实测（`verify_knowledge_rag.py`）间隙由 `(0.0968, 0.1171)` 变为
   **`(0.0930, 0.1180)`**，`min_score = 0.11` 仍落在间隙内 → 保留。该脚本现会
   **实测并打印间隙**，今后改语料会被迫重算，而不是沿用旧结论。
3. **回归当场抓到一处话题重叠**：新增「堂食与外卖的利润差异」后，
   `recall@1` 掉到 29/30 —— 查询「外卖和堂食哪个更赚钱」首位命中了旧的
   「外卖平台抽成」（因为那条正文里也写着"外卖单毛利显著低于堂食"）。
   处置：**删掉旧条目里的利润比较内容**，把它收敛为纯费率事实
   （旧条答"平台收多少"，新条答"同一笔流水谁更赚"），而不是去改测试迁就代码。
   修完 `recall@1 = recall@3 = 30/30`。

## 七、量化示例（宁波 30㎡ 奶茶 / 自报月流水 8 万 / 月租 1.2 万 / 2 人 / 蜜雪冰城）

| 指标 | 值 |
|---|---|
| 毛利率（产品口径） | **65.0%**（= 1 − 物料 32% − 损耗 3%） |
| 外卖抽成占流水比 | **7.7%**（= 35% × 22%） |
| 扣渠道后毛利率 | **57.3%** |
| 变动成本率 v | **50.7%**（物料 32 + 损耗 3 + 外卖 7.7 + 场地 6 + 税 2） |
| 固定成本 / 总成本 | ¥37,777 / ¥78,336 |
| 月净利 / 净利率 | **¥1,664 / 2.1%** |
| 盈亏平衡月流水 | **¥76,627** |
| 安全边际 | **4.22%（¥3,373）**——流水再跌 3,373 元就转亏 |
| 盈亏平衡月租 | ¥13,663（自解）/ ¥13,650（引擎二分） |
| 租金余量 | ¥1,663/月 |
| 品牌对标 | 蜜雪公开基准 ¥125,532/月 → **做到 63.7%** |

诊断文本会据此给出方向：**经营面本身没问题（超六成基准），瓶颈在成本结构或租金**
——而不是先让店主加推广预算。这是"有依据的诊断"与"营销玄学"的分界。

## 八、局限声明（必须与结论一同呈现）

1. **成本率是假设区间不是实测**：物料占比、外卖占比、场地附加、税、损耗
   与选址侧**共用同一套假设**（`SCENARIOS` 三档）。用户若有真实账目，
   应把这些率替换为实测值——引擎已支持传入，但**本系统不替用户认定真值**。
2. **品牌基数是品牌平均且披露期不同**（蜜雪为 2024 前 9 个月、茶百道为 2023 全年），
   不是同商圈同面积可比店。
3. **不含开业爬坡期差异**，也不含一次性损失（装修返工等）。
4. **营销语料只到"机制性事实"层级**：它说明"外卖占比是成本杠杆""评分影响曝光"，
   **不给**"投 X 元买多少单"这类系数——因为本系统没有该数据的实测支撑。
5. **`v ≥ 100%` 时不给安全边际**（卖得越多亏得越多），此时输出明确说明原因，
   不返回空值让上层误读。

## 九、回归覆盖

新增 `src/analysis/verify_store_diagnosis.py`（**41 项断言，零 API**，已纳入
`run_regression.py` 离线门禁组）：

| 组 | 锁什么 |
|---|---|
| T1 口径 | 毛利率可复算、扣渠道后 = 毛利率 − 7.7%、口径文本、率不随规模变 |
| T2 不换模型 | 11 项成本与 `estimate_profit` 逐项相同；总分项自证；**命名陷阱哨兵** |
| T3 安全边际 | `F/(1−v)` 自洽；流水置平衡点净利≈0；低于平衡点边际为负 |
| T4 双算法互校 | 自解租金临界 vs `solve_rent_limits` 二分；租金余量恒等式 |
| T5 对标纪律 | 有数据给、无数据（茶百道/奈雪/喜茶）必须是 `None`；不传品牌不对标 |
| T6 异常输入 | 无流水/≤0/非数字/只给日单量 → 一律 `ValueError`，不返回空壳 |
| T7 不估流水 | 无 `月流水估算` 字段；成本按自报值算；日单量折算 |
| T8 诊断文本 | 高流水/亏损/租金越界各自触发对应结论；局限与结论同出 |
| T9 确定性 | 同输入两次逐位相同 |

同时更新 `verify_knowledge_rag.py`（现 **18 项断言**）：语料哨兵 24→30、
新增 6 条标注查询、**source 覆盖率与注入可见性**、**阈值间隙实测**。
