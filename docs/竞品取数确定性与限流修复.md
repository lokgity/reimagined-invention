# 竞品取数确定性修复：限流被当成"没有数据"

> 状态：**已实施并通过验证**
> 时间：2026-09-15
> 触发问题：同一地址、同一品牌，两次评分得到的月流水不同（差约 2.3 倍），报告不可复现
> 涉及文件：`src/engine/competitor_insight.py`（主）、`src/engine/scoring.py`、`src/engine/brands.py`、`src/agent/agent_graph.py`、`src/ui/app_chainlit.py`、`src/analysis/test_veto.py`
>
> **📌 同日后续（单位口径第二次修正）**：本文中出现的客单价 `¥7` 是**高德单杯价**，
> 曾被当成**每单金额**使用。正确口径为公开披露的**每单金额**（蜜雪 ¥11.4）。
> 相关修正见 [`品牌级公开数据与客单价口径修正.md`](./品牌级公开数据与客单价口径修正.md)；
> 本文 §4.3 / §五 / §八 / §九 已就地标注。**本文其余部分（复现性修复）不受影响。**

## 一、症状

`brand_price_reference()` 每次评分都实时打高德 `/v3/place/around`，结果不入库、不冻结。
表现为 `校正客单价` 在 **¥7 与 None 之间跳变**：

- 取到值 → 客单价 ¥7 → 月流水 89,190
- 取不到 → 客单价退回品类画像 ¥16 → 月流水 203,863

**差 2.29 倍，正好等于校正倍数 16/7。** 结论（是否亏损、是否触发一票否决、回本周期）随之反转。

## 二、量化证据：数据源本身是确定的

修复前的探测（`_probe_priceref` / `_probe_amap`，各连续调用 6~12 次）：

> ⚠️ 溯源说明（2026-09-15）：这两个探针是**一次性诊断脚本**，其原始输出文件在
> 当日临时文件清理中已被删除，**未保留原始日志**。下表是当时读取日志后记录的结论；
> 结论本身已由常驻回归 `verify_price_ref_determinism.py`（缓存命中 0 API、逐字段一致、
> 失败态稳定）与 `verify_brief_smoke.py` 独立复现，不依赖那份日志。

| 观测 | 结果 |
|---|---|
| 成功时 POI 条数 | 恒定（湖滨 in77 = 25/25、count=78；天一广场 = 25/25、count=63） |
| 成功时同品牌样本数 | 恒定（天一广场蜜雪恒 3 家、in77 恒 5 家） |
| 成功时同品牌人均中位 | 恒定 ¥7.0 |
| 连续无间隔调用 | **第 5 次起**返回 `status=0, infocode=10021, CUQPS_HAS_EXCEEDED_THE_LIMIT` |
| 间隔 2s 再调 | **全部恢复** OK |

**结论：非确定性 100% 来自高德 QPS 限流，不是数据源抖动。** 这一条决定了修法的方向——不是"扩大采样降低方差"，而是"别把限流当数据"。

## 三、根因：三层叠加

### 3.1 限流被静默吞成"空结果"

```python
# 旧代码
try:
    data = http_get(amap_url('/v3/place/around', params), timeout=20)
except Exception:
    return []
if data.get('status') != '1':
    return []          # ← 限流走到这里，和"这一带没有竞品"变成同一个值
```

`http_get` 的 `retries=4` 只在**网络异常**时生效；收到 HTTP 200 + `status=0` 时它认为请求成功，直接返回，**限流不重试**。

### 3.2 下游据此写出假结论

```
'周边 0 家同类门店里没抓到「蜜雪冰城」的人均消费字段（高德未收录或 biz_ext.cost 为空），沿用品类画像假设'
```

明明是限流，却说成"高德未收录"。用户会直接得出**"这个商圈没有蜜雪冰城"**的相反结论。这是本次修复中最严重的部分——它不只是算错数，而是陈述了一个错误事实。

### 3.3 结果不落盘

每次评分重打接口，抖动直接进流水，且同一分析链路里 `brand_price_reference` 与 `competitor_brief` **用完全相同的参数各打一次**，把限流概率翻倍。

## 四、修法

### 4.1 抓取层带出失败原因，不再丢弃

`fetch_around_raw()` 返回 `(pois, meta)`，`meta` 含 `ok / info / infocode / err / tries / quota`。

按 infocode 分两类，决定"重试有没有意义"：

| 集合 | infocode | 含义 | 处理 |
|---|---|---|---|
| `RETRYABLE_INFOCODES` | 10021 / 10020 / 10004 | 单位时间 QPS 超限 | 退避重试 0.4s → 0.9s → 1.8s（总 < 3.2s） |
| `QUOTA_INFOCODES` | 10003 / 10019 | 日配额耗尽 | **不重试**，明确告知"今天取不到"，避免用户以为"高德没这个数据" |

网络层重试降为 `retries=2`（`http_get` 默认 4 次的退避是 2+4+6+8 = 20s，评分路径上太久）。

### 4.2 持久化冻结缓存

`data/competitor_cache.json`，**缓存的是原始 POI 快照**（不是某个品牌的价格），因此同一坐标换品牌也复用同一份数据：

- 键：`{lng:.4f},{lat:.4f}|{品类}|{半径}|{limit}`
- TTL：**成功 30 天**（人均消费以月/季计）、**失败 180s**（够让一次会话内数字不跳，又能在限流解除后自愈，不会把一次抖动固化很久）
- 写入：先写 `.tmp` 再 `os.replace` 原子替换
- 上限：400 条，按时间淘汰

**副产物**：`brand_price_reference` 与 `competitor_brief` 现在共享同一条缓存，同一地址的评分从 2 次 API 降为 1 次，重复分析降为 0 次。

### 4.3 口径按四种状态分流，互不混同

`brand_price_reference` 返回值新增 `抓取状态 / 来源 / 取证时间`：

| 状态 | 含义 | 口径怎么写 |
|---|---|---|
| `ok` | 取到同品牌价格（或命中公开数据） | 正常校正，附来源与倍数 |
| `public_only` | **取数失败但该品牌有公开披露的每单金额** | 直接用公开值校正，并声明"**不受本次取数失败影响**" |
| `fetch_failed` | **限流/配额/网络失败**，且无公开数据 | 说清失败原因 + **明确声明"这不代表附近没有该品牌"**，并用本地库交叉验证 |
| `no_same_brand` | 取数成功、周边确实无该品牌 | 才可以说"周边 N 家里没抓到" |
| `self_brand` | 自创品牌/不加盟 | 说清"这是口径定义" |
| `underpowered` | 同品牌仅 1 家 | 不构成换算依据，但把单杯价报出来并点明它**不是**每单金额 |

> `public_only` 与 `public_report` 口径来源是**同日第二次修正**（单位口径）时补上的，
> 见 [`品牌级公开数据与客单价口径修正.md`](./品牌级公开数据与客单价口径修正.md)。

### 4.4 限流时用本地库交叉验证存在性

`_local_brand_presence()` 查本地预抓取库（`zj_poi.db`，44,233 条）。**本地库是 `place/text` 抓的、没有 `biz_ext`，所以不含人均消费字段，不能用来算价格校正**——它只能回答"这一带到底有没有该品牌"。

当 API 失败而本地库显示该品牌在 1km 内有门店时，口径会说：
> 本地预抓取库显示该品牌在周边 1000m 内有 N 家门店（…），说明该品牌在当地确实存在，只是本次没能取到价格。

这是对"限流 = 附近没有这家店"这一误导的直接反驳。

### 4.5 `score_site` 五种状态分别出声，不留沉默回退

修复前 `no_same_brand` 与限流失败**都不产生任何 warning**，静默沿用品类画像。现在：

- `fetch_failed` → ⚠️「客单价**未校正，且不是因为没有该品牌**」
- `self_brand` → ℹ️「按品类画像测算：自创品牌没有同品牌连锁可参照（口径定义，不是没查到）」
- `no_same_brand` → ℹ️「1km 内没抓到该品牌门店的人均字段」
- `underpowered` → ⚠️「不足 2 家不构成校正依据，若真实定价接近 ¥X 则流水高估 N 倍」
- 正常校正 → ℹ️ 附「实时/缓存取数，取证时间」

取数溯源同时写入 `result['客单价校正']` 与看板「竞品数据来源」行。

## 六、取舍与局限

1. **失败缓存 180s 是刻意的折中。** 完全不缓存失败 → 同一会话内数字仍会跳（限流解除前后不一致）；缓存太久 → 把一次瞬时抖动固化。180s 的定位是"一次会话内稳定 + 3 分钟后自愈"。
2. **本地库只能证存在性，不能替代价格校正。** 限流时报告里的流水仍是按品类画像算的，这一点在 warning 里明说了"请勿据此签约"。
3. **缓存按坐标 4 位小数（≈11m）分桶**，不同铺位各存一份。牺牲了一点命中率换取"同一输入必然同一结果"的严格可复现性。
4. **限流窗口不可控。** 高德个人 key 的 QPS 上限是平台侧配置，本次实测"连续 5 次触发、间隔 2s 恢复"，但该阈值不保证稳定；退避重试只能覆盖瞬时限流，日配额耗尽仍需等次日。
5. **未做的**：本地库若能补抓 `extensions=all`（含 `biz_ext.cost`），限流时就能直接兜底出价格而不只是存在性——这需要重跑一次全省预抓取，尚未做。

## 七、顺带修掉的三个既有缺陷

1. **`clear_cache()` 让缓存一次都没落盘，且无任何报错。**
   路径初始化被绑在 `if _CACHE_MEM is None` 里，而 `clear_cache()` 先把 `_CACHE_MEM` 置成 `{}`，于是 `_CACHE_PATH` 永远是 `None`，`_save_cache()` 静默早退。已把路径初始化拆成独立的 `_ensure_path()`，并让写盘失败打 stderr + 记录到 `CACHE_SAVE_ERROR`。
2. **`competitor_brief` 里 `lines` 未初始化就直接 `append`** → `NameError`，会让整个竞品分析链路崩掉。由 `verify_brief_smoke.py` 在真实路径上抓到。
3. **`analyze_competitors` 不传 `fetch_meta` 时会被误标成"取数失败"** → 改为三态：实时 / 缓存 / 取数失败，未传时标"未标注"。

另外把 `自创品牌` 从"取数失败"里分出来（`engine.brands.is_self_brand()`）：自创品牌**定义上**就没有同品牌连锁可参照，不该去查、也不该报成"附近没抓到"，顺带省掉一次 API 调用。

## 八、`test_veto.py` 案例 F 的断言修正

案例 F 原有 3 条断言在修复前**就已经是红的**。最初判断是"测试数据陈旧"，追下去发现
真正原因是引擎口径问题（见第九节）。这里先记录测试本身怎么改。

证据链（确认与本次取数改动无关）：

- 该案例传入的是**冻结的** `price_ref=PRICE_REF`，根本不进 `competitor_insight`；
- 断言涉及的 `profit / veto / rent_limits` 完全由「免租净利 − 租金」决定，实测
  `3322 − 6000 = −2678` 与输出逐位吻合；
- 原断言用月租 ¥6,000，在"品类画像 ¥16"口径下可行（净利 +3.0 万、回本 5.6 月）；
  换成同品牌真实人均 ¥7 后，该铺子免租净利只剩 ¥3,322、24 个月回本上限降到 ¥500，
  于是 ¥6,000 必然亏损、否决**正确**触发。

**第一次修法是错的。** 当时把月租从 ¥6,000 改成 ¥500，等于把用例挪到一个不现实的点上
让它变绿（天一广场 30㎡ 不存在 ¥500 的租金）；而且原测试只验内侧、没有断言挡住
"把阈值挪到刚好能过"，这正是它当初能悄悄失效的原因。

现在的修法：`RENT_OK` / `RENT_BAD` 均从引擎自己解出的临界点**动态构造**，两侧都验。

| | 内侧 `cap−50` | 外侧 `cap+500` |
|---|---|---|
| 期望行为 | 放行、结论=推荐 | 触发否决 |
| 实测（cap=¥500，当时的 ¥7 口径） | 月租 ¥450 → 净利 ¥2,872、回本 23.7 月 → 放行 | 月租 ¥1,000 → 否决=True |

> **⚠️ 后续（2026-09-15 当日第二次修正）**：上表的 `cap=¥500` 是**错误单位**下的产物。
> 追查发现引擎把高德 `biz_ext.cost`（**单杯价**）当成了**每单金额**，把低价品牌流水
> 压低约 1.4~1.7 倍。口径改正为「每单金额」后：
>
> - `PRICE_REF` 由 ¥7（单杯）改为 **¥11.4（每单，蜜雪招股书）**；
> - 该案例的临界点 `cap` 由 ¥500 升到 **¥19,450**，月租 ¥12,000 由"账算不过来"
>   **翻为"推荐"**（`test_veto.py` 已把这一翻转锁成断言）；
> - **口径哨兵**由「免租月净利 = ¥3,322」改为 **¥22,265**。
>
> 详见 [`品牌级公开数据与客单价口径修正.md`](./品牌级公开数据与客单价口径修正.md)。
>
> **后续 3（2026-09-18）：品牌 uplift 整表重标定 v6**。上面的 `cap=¥19,450` 与哨兵
> `¥22,265` 是 **v1 uplift**（蜜雪 1.1343）下的值。v6 换成代理商圈口径（1631 家 / 28 品牌）
> 后蜜雪 → **1.1903**，本案例整条链路上移（实测）：流水 ¥99,552 → **¥104,467**（+4.93%）、
> 月净利 ¥10,265 → **¥12,688**、回本 12.6 → **11.0 月**、`cap` → **¥21,900**、
> 盈亏平衡月租 → **¥24,700**、免租月净利 → **¥24,688**、经营评分 70 → **76**，
> 结论由"谨慎推荐"上移为 **"推荐"**。`test_veto.py` 三处哨兵已重标定，
> 并写明"本节对 uplift 敏感"。归因已钉死：零 API 探针把蜜雪回灌 v1 的 1.1343，逐位复现旧值。
> 详见 [`品牌溢价整表重标定v6-实施记录.md`](./品牌溢价整表重标定v6-实施记录.md)。

另加两条断言：

- 「内侧铺子回本周期确实落在红线内」——验语义，不只验触发位；
- **口径哨兵**：锁住「免租月净利 = ¥3,322」。谁改了流水/成本结构这行会红，
  提醒回来复核本节所有阈值类断言是否还成立。

## 九、附注：客单价校正的「单量口径矛盾」（**已修，见 `品牌级公开数据与客单价口径修正.md`**）

> **⚠️ 标题更新（2026-09-15）**：本节原记为"已发现，未修"。同日追查发现，
> 本节 9.2 表里"同品牌 ¥7"这一行的**单价口径本身就是错的**——高德 cost 是
> **单杯价**、不是每单金额。改正为"公开披露每单金额 ¥11.4"后，"过校正"的程度
> 大幅缩小（见下方 9.3 的补充表）。**本节保留原始推理过程**，但结论请以下方
> 修订后的表与 [`品牌级公开数据与客单价口径修正.md`](./品牌级公开数据与客单价口径修正.md) 为准。

修案例 F 时挖出来的，比原来的问题严重——它影响**所有**品牌的流水测算。

### 9.1 事实

| 项 | 值 | 出处 |
|---|---|---|
| `profile['daily_sales']` | 250 单/天 | 奶茶品类画像 |
| 该值的含义 | **83 家中位水平门店**的日单量 | `scoring.py` 锚点注释 |
| 83 家样本的品牌构成 | 蜜雪 **14 家（16.9%）**、个体杂牌 10 家、其余 21 个品牌各 1-6 家 | `stores_calib.csv` |
| 隐含单价 | ¥16（品类画像） | `profile['price']` |
| → 中位门店月营业额 | 16 × 250 × 30 = **¥120,000** | 推算 |

流水公式（`estimate_monthly_sales`）：

```
daily   = base_daily × (D×P)/REF_DP × 面积修正 × 城市修正 × 品牌溢价 × 0.6
monthly = daily × price × 30          # ← daily 里没有 price
```

**`daily` 不含 `price`**，所以客单价校正只换了"一杯多少钱"，没换"一天卖多少杯"。
而 `base_daily` 是**跨品牌混合**中位门店的单量，它隐含绑定的是 ¥16 那一档定价。

### 9.2 量化（宁波天一广场，30㎡，投入 20 万，2 人，蜜雪冰城）

| 口径 | 月流水 | 月净利 | 回本 | 盈亏平衡月租 | 回本上限 |
|---|---|---|---|---|---|
| 品类画像 ¥16 | ¥139,722 | **+30,069** | 5.6 月 | ¥42,050 | ¥39,250 |
| 同品牌 ¥7（单量不变） | ¥61,128 | **−8,678** | 不可能 | ¥3,300 | **¥500** |
| ✅ 同品牌**每单金额** ¥11.4（口径修正后） | ¥99,552 | **+10,265** | 12.6 月 | ¥22,250 | **¥19,450** |

上一行的 ¥7 是"单杯价当每单"的**错误口径**；末行才是修正后的正确口径。
同一个位置、同样 **291 单/天**，若换成喜茶 ¥24 → ¥209,520/月，**差 3.4 倍**。
现实中同商圈两者的营业额差距远小于此——**低价换高频**。

反推：月租 ¥12,000 下，客单价 ¥11.4 需要约 **409 单/天** 才能在营业额刚性端 24 个月回本。
蜜雪冰城单店做到 400 单/天并不罕见。

### 9.3 结论（含口径修正后的修订）

原判断："这是**过校正**：把方向从「高估」翻成了「低估」，真实值在两者之间。"

**修订**：所谓"过校正"的程度，一部分来自**单价口径错误**，不只是弹性未标定。
分开看：

- **单价口径**：¥7 是**单杯价**，不是每单金额。正确值为**公开披露的 ¥11.4**。
  偏差从"低估 2.29 倍"缩小到"画像 ¥16 相对 ¥11.4 偏高 40%"。
- **单量弹性**：`base_daily = 250` 是跨品牌混合中位，不随客单价联动——这才是
  真正**未标定**的自由度，仍由口径区间呈现。

所以之前文档与 warning 中"蜜雪流水高估 2.3 倍"的说法**既用错了单价口径、
也混入了弹性问题**，现已全部改为"**每单金额**校正 + 口径区间"两件事分开讲。

**当时未修的原因**：要定住这个值需要**品牌级日单量基准**（或价格-单量弹性）。
现有 83 家样本里蜜雪只占 14 家，且 `stores_calib.csv` 只有
`名称/经度/纬度/外卖月售/品牌/吸引力系数/商圈` 七个字段、**没有营业数据**。
宁可标注不确定，也不编一个系数出来。

### 9.4 附带发现：月流水↔净利非单调

反推过程中出现的阶跃：

| 月流水 | 月净利 | 回本 |
|---|---|---|
| ¥55,000 | −4,623 | 214 月 |
| ¥60,000 | **−7,918** ↓ | — |
| ¥90,000 | +1,112 | 30.0 月 |
| ¥95,000 | +3,577 | 21.9 月 |
| ¥120,000 | **+10,142** ↓ | 12.7 月 |

原因是 `derive_staff` 按日单量**台阶跳**（人数 = ⌈日单量 / 人均日单量⌉），
人数跳一档，人工成本台阶式上升。

- 对 `solve_rent_limits` **无影响**：它沿**租金**维度二分，而人数由 `sales_est`
  决定、与租金无关，所以净利对租金严格单调，二分收敛性成立；
- 但"提高流水一定改善回本"这个直觉**不成立**，写建议时不能这么说。
