## 1. CoCo 这类品牌查不到客单价

### 1.1 我的理解
你看到的现象是：给一个像 CoCo 这样很常见的奶茶品牌，系统没能拿到它的客单价，最后用的是品类默认值。你问两件事：**为什么会这样**、**能不能自己把数据补进数据库**。

### 1.2 根因（三层，逐层都有确证）

**第一层：公开经营数据表里根本没有 CoCo。**
`src/engine/brand_store_metrics.csv` 全表只有 **6 行**（蜜雪/古茗/沪上阿姨/霸王茶姬/茶百道/奈雪），入选口径高度一致——**每一行都带证券代码**（2097.HK / 1364.HK / 2589.HK / CHA.O / 2555.HK / 2150.HK），来源列全部指向"招股书 / 年报"。CoCo 的运营主体**未上市、无招股书**，所以按这张表的契约它进不来。表自己的文档写明：**"未披露的字段留空，不做插补"**（`docs/品牌级公开数据与客单价口径修正.md:187`）。

**第二层：高德取数不是"失败"，而是"没采样到"。**
抓取层用的是 `/v3/place/around`，关键词固定取品类画像的第一个词（奶茶 → `'奶茶'`），**固定只取半径 1km 内最近的 25 家**（`src/engine/competitor_insight.py:189-201`）。实测三个点位：

- 宁波天一广场：返回 25 家，**CoCo 不在其中** → 状态 `no_same_brand`
- 杭州临平：同样 `no_same_brand`
- 宁波鄞州万达：抓到了 `CoCo都可(后庙店) cost=12.0`，但**同品牌只有 1 家**，低于门槛 `MIN_SAME_BRAND_SAMPLES = 2`（`:278`）→ 状态 `underpowered`

注意 `meta.ok=True`——**接口是成功的**，所以这跟限流/配额无关，是"品牌没进 top25 采样"和"样本数不够"两个独立的采样问题。

**第三层：本地库结构上就没有价格。**
`data/zj_poi.db` 只有一张 `poi` 表、10 个列（`id/city/adname/category/poi_type/name/address/lng/lat/created_at`），**没有任何价格/人均字段**（建表见 `src/data/query.py:17-31`，落库 `src/data/fetch_poi.py:110-119`）。它由 `/v3/place/text` 抓取，本来就不带 `biz_ext`。代码里已显式承认这点（`competitor_insight.py:313-320`）。

**缺了会怎样**：回落到硬编码画像价 **奶茶 ¥16/单**（`src/config.py:90`），并在 `warnings` 里明确写"未校正 + 原因"（`src/engine/scoring.py:668-708` 有 6 路文案分流）。所以**不静默**——但流水与回本数字确实按 ¥16 算。

**顺带发现一个更值得修的缺口**：好几个品牌**库里有、代码认不出**——`书亦烧仙草`（库内 31 家）、`益禾堂`（10）、`贡茶`（10）、`快乐番薯`（17）、`7分甜`（2）都在本地库里，但 `BRAND_KEYWORDS` 里没有它们的词条 → 品牌识别返回空 → 走的是"个体户"路径。**这是纯代码补词，零数据风险。**

### 1.3 方案（分层，各带来源等级）

**补什么、从哪补**，我建议分三级，每级在 UI 上都标出来源等级，不要混成一种"官方数据"：

| 级别 | 来源 | 覆盖 | 是否可溯源 | 建议 |
|---|---|---|---|---|
| **A 级（实时、可溯源）** | 高德**品牌定向搜索** | CoCo 及所有"有门店但不在 top25"的品牌 | 是（高德实时），带取证时间 | **首选，优先做** |
| **B 级（公开披露）** | 招股书/年报（现有 `brand_store_metrics.csv` 契约） | 仅上市公司 | 是 | 保持现状，继续只收披露值 |
| **C 级（行业参考）** | 第三方行业数据（连锁经营协会报告、行业数据库等） | 广 | 需标"行业参考，非披露" | **可选**，需新增来源等级列 |

**具体动作**：

1. **改用"品牌定向查询"补 A 级**：除了现有的 `/place/around` 取周边竞品，**再补一次 `/v3/place/text`，keywords 直接用品牌名**（如 `CoCo都可`）+ 城市限定，`extensions=all` 拿 `biz_ext.cost`。这样能拿到该品牌在候选点位附近**所有**门店的真实单杯价，直接解决"不在 top25"和"样本不足"。这是**唯一一个既真实、又可实时、又不引入编造**的补法，我建议作为主方案。
2. **放宽同品牌样本门槛的判定方式**：现在 ≥2 家才算。可以改成"≥1 家时给出**单点参考值 + 明确标注 n=1 不可作换算依据**"，让用户看到"高德实测 ¥12"而不是只看到"没数据"。注意：**显示 ≠ 生效**，n=1 仍可不参与流水计算，但信息要给到。
3. **补 `BRAND_KEYWORDS`**：把库里已有但认不出的品牌词补上（书亦烧仙草/益禾堂/贡茶/快乐番薯/7分甜/甜啦啦/快乐柠檬/茶颜悦色/阿水大杯茶 等）。零风险，且能立刻让这些品牌的竞品识别、UPLIFT 匹配生效。
4. **（可选）C 级表**：新建一张 `brand_price_estimates.csv`，与 A/B 级**分开存放**，必须带 `来源` 与 `口径` 列，UI 上以"行业参考值"呈现，绝不与披露值混用同一标签。
5. **修一个坑**：`奈雪的茶` 在 CSV 里的 key 与关键词归一化结果（`奈雪`）不匹配，导致该行**永远取不到**（`src/engine/brands.py:360-364`）。该行本身还填的是区间字符串 `6800~8900`，`_num()` 直接判无效。

### 1.4 风险 / 需你拍板
- **C 级要不要做？** 这是唯一会打破"每个数字可回溯到招股书/年报"这条既有契约的动作。做，就要接受来源等级变复杂；不做，很多非上市品牌永远只能是"品类默认值"。
- **n=1 的门槛**：显示但不生效，还是干脆放宽到生效？我建议"显示不生效"。

## 2. 历史会话：去掉中间子页面 + 回放聊天内容

### 2.1 我的理解
现在点一条历史会话，先弹出一个只读的中间页（`#zl-page-ov`，标题"历史会话 · xxx"），要再点一次「继续对话」才真的进入。而且进去之后**只有右栏数据面板 + 一个 PDF**，之前和 AI 的对话内容不见了。你要：**去掉中间这一步**，并且**把聊天内容也恢复出来**。

### 2.2 根因
流程确实是**两段式**（`public/sidebar.js`）：

- 点击 → 事件委托 `[data-open]` → `openHistory(id)`（`:1041-1046`、`:1025-1040`）→ 只 `fetch('/public/sidebar.json')` → `renderHistPage()`（`:2485-2506`）渲染覆盖层，**不发任何后端请求**。
- 「继续对话」按钮 `#zl-pg-cta`（`ensurePageOv`，`:2444-2461`）→ `sendCmd('##打开:'+id+'##')` → `closePage()`。
- 后端 `process_open_conv()`（`src/ui/app_chainlit.py:782-807`）**只做三件事**：切 `state`、`render_analysis_dashboard()`（右栏 + 新发一条带**重新生成**的 PDF 的消息）、发一句"✅ 已切换到历史会话"。它的 docstring 原文就写着 **"不向当前页面回放消息"**（`:783-784`）。

**好消息**：历史消息**是有持久化的**——`data/conversations.json` 里每个会话都有 `state.messages = [{role, content}]`（`src/agent/conversation_store.py:54-76`）。所以"回放"不缺数据，缺的是**往对话框注入消息的通道**。

### 2.3 方案

**第一步：去掉中间层（简单）**
把 `openHistory` 里"渲染覆盖层"改成"直接走原 `##打开:` 的动作"，即点击一步到位。要点：
- 保留覆盖层作为**其它用途**（知识库/专家卡片页仍用它），只改历史项这条路径；
- 注意 `layoutBar()` 与覆盖层的互斥逻辑（`:2210-2215`）要同步——不再打开覆盖层，专家条就不该被隐藏。

**第二步：回放聊天内容（要选技术路线）**

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 后端重发消息（推荐）** | `process_open_conv` 里按 `state['messages']` 逐条 `await cl.Message(...).send()`，用户侧用 Chainlit 的用户消息类型（若 2.11 提供 `cl.UserMessage`） | 是**真消息**，样式/交互一致，顺序天然正确 | ⚠️ 要验证 Chainlit 2.11 是否暴露用户消息构造器；且**不能写回 `state.messages`**，否则重复累积 |
| **B. 前端 DOM 注入** | 直接往聊天列 `insertBefore` 一个"历史回放"区块 | 不依赖后端 | 不是真消息；**下一条新消息会插到它后面，顺序错乱**；与现有 `hideCmdBubbles`/emoji 观察器可能打架 |
| **C. 只做"摘要 + 折叠"** | 不逐条回放，只发一条可展开的"历史记录"消息 | 最简单、最稳 | 不满足你"把分析的内容也展现出来"的原意 |

我倾向 **A**，但**必须先做一个最小技术验证**（确认 Chainlit 2.11 的消息构造 API），验证不通过再退到 C。

**第三步：顺手解决 PDF 重复生成**
现在每次打开历史会话都会**重新跑一遍 Playwright 生成 PDF**（`app_chainlit.py:1412`）。建议把 PDF 字节缓存到 `data/reports/<conv_id>.pdf`，历史打开时直接复用；这同时是 §4 的一个提速点。

### 2.4 需你拍板
- 回放范围：**全部消息**，还是只回放最近 N 条 + 一个"查看更早"入口？（历史**没有上限**，长会话全量回放会很长）
- 回放出来的消息，要不要**可继续对话**（即在它后面正常接着聊）？——方案 A 天然支持。

## 3. PDF 打开后被遮挡

### 3.1 我的理解
分析完成后有一条带 PDF 附件的消息。点开 PDF，它显示在**中间层**，会被别的东西挡住，你要求它打开时**在最上层、完全无遮挡**。

### 3.2 根因（非常明确：就是一个 z-index 数字问题）
PDF 由后端用 `cl.Pdf(..., display='inline')` 发送（`src/ui/app_chainlit.py:233-236`、`1415-1418`）。Chainlit 前端把它渲染成一个缩略图，点击后打开 **Radix Dialog 全屏模态**，其层级是：

- 遮罩 overlay：`fixed inset-0 z-50` → **z=50**
- 内容 content：`fixed ... z-50` + `translate`（自建层叠上下文），被组件传入的 `z-[60]` 覆盖 → **z=60**
- Portal 容器回落到 `document.body`

而项目自己在 `document.body` 上挂的浮层全部**高于它**：

| z-index | 元素 | 出处 |
|---|---|---|
| 2050 | `#zl-xbar` 输入框上方专家条（含面板/toast） | `sidebar.js:596-597` |
| 2000 | `#zl-page-ov` 中间覆盖层 | `sidebar.js:528` |
| 300 | `#zl-settings` 设置全屏遮罩 | `sidebar.js:501` |
| 125 | `#zl-gear` 齿轮 | `sidebar.js:496` |
| 95 / 90 / 80 / 79 | 拖宽热区 / 命令排队条 / 左栏 / 右栏 | `sidebar.js:458/381/139/192` |
| **50 / 60** | **Chainlit PDF 弹层** | Chainlit bundle |

所以**左栏、右栏、齿轮、专家条全都会盖在 PDF 上面**。作者自己其实踩过同类坑并留了注释（`sidebar.js:3036-3041`，讲背景竖线为了不遮挡内容而用 `z-index:-1`）。

### 3.3 方案
**提高 PDF 弹层，而不是压低项目浮层**（更安全，不动既有层级关系）：

1. 在项目 CSS 里命中 PDF 弹层的 overlay 与 content（可用 `[role="dialog"]` + 其同级的 overlay 属性选择器），把 `z-index` 提到项目最高层之上（例如 3000+）。
2. **打开 PDF 时把专家条 `#zl-xbar` 隐藏**——它是最高的那个（2050），且悬浮在画面下部，最容易压住 PDF 底部。可以复用已有的"覆盖层打开就隐藏专家条"机制（`sidebar.js:2210-2215`），把"PDF 弹层打开"也纳入该判定。
3. **反向检查**：把 z-index 调高后，要确认 Chainlit 自己的 toast/提示不会因此被盖住（需要实机点一次看）。
4. **验收方式**：实机打开 PDF，截图逐像素确认无遮挡（沿用现有 UI 门禁的截图比对方法），并断言 `document.elementFromPoint()` 在 PDF 中心取到的是 PDF 本身。

### 3.4 风险 / 需拍板
- Chainlit 是 minified 的第三方 bundle，选择器依赖其内部结构（`z-[60]`、`[role="dialog"]`）——**升级 Chainlit 版本可能失效**。要不要加一条"层叠哨兵"断言（版本升级后自动报警）？
- ⚠️ 一个不能确定的前提：如果运行在嵌入式/Copilot 形态（`window.cl_shadowRootElement` 被赋值），弹层会挂进 shadow root，层叠关系要重算。本项目是独立部署，按 `document.body` 处理；**需要你确认部署形态只有一种**。

## 4. 分析耗时

### 4.1 我的理解
走完所有输入步骤、进最后一步分析时，等待有点久。你想知道**有没有办法再快一点**。

### 4.2 现状：耗时的来源（按代码常数排序，非实测）

| 排名 | 来源 | 位置 | 常态 / 最坏 |
|---|---|---|---|
| 1 | **`interpret` 的 LLM 调用** | `agent_graph.py:1843`；单 provider timeout 120s、整链预算 180s（`llm.py:44`） | 常态 5~30s；降级链最坏 180s |
| 2 | **VLM 门头照**（仅候选带图时） | `agent_graph.py:1730-1742`，`wait_for(75)`、单模型 60s | 3~15s；最坏 75s |
| 3 | **地图瓦片**（新位置首次） | `app_chainlit.py:1485-1494`，**9 张串行**，单张 timeout 8s，失败还依次试 2 个源 | 已缓存 ~0.1s；新位置可能数秒~数十秒 |
| 4 | **竞品口碑高德请求** | `agent_graph.py:1767` | 缓存命中 ~0s；未命中 0.5~3s |
| 5 | **PDF（Playwright + Chromium）** | `app_chainlit.py:1412`、`report_pdf.py:317-328` | 1~5s，首启更久 |
| 6 | **前端展示延迟** | `sidebar.js:3147-3149` 固定 **2500ms** 轮询 | 固定 +0~2.5s |
| 7 | `score_site` 本地计算 | `query.py:80-94` 每次全类目扫描 + Python 逐行 haversine；`get_conn()` 每次重跑建表语句 | 几十~几百 ms |
| 8 | 0.6MB 的 `dashboard.json` 每 2.5s 无条件 fetch | `app_chainlit.py:332`、`sidebar.js:3115` | 本地影响小 |

**已存在的优化**（这块其实做得不错）：竞品 POI 缓存 30 天、geocode 缓存、地图瓦片落盘、`realtime` 进程内缓存、本地库优先、纯本地反解租金（0 API）、阻塞调用全部 `to_thread`、各步骤失败不阻塞主流程。

**明确的"可并行却串行"**（全项目 **零 `asyncio.gather`**）：
1. `analyze_node` 里 **VLM（:1738）与竞品抓取（:1767）互不依赖**，却一个 await 完再 await 下一个；
2. `_build_shop_map_png` 的 **9 张瓦片串行下载**；
3. `render_analysis_dashboard` 里 **地图 / 写面板 / 生成 PDF** 三件互不依赖的事串行；
4. `reverse_match_node` 的 4 个品类逐个重算（`:1312-1317`）。

**一处病理路径（隐患）**：`engine/realtime.py:62` 的 `http_get` **没传 `retries`**，于是吃默认 `retries=4` + `2×(n+1)` 睡眠 → 单个类目最坏 **4×10s 超时 + 20s 睡眠 ≈ 60s**。同项目里 `competitor_insight.py:209-211` 已经显式把它降到 2 并写明理由（"退避 2+4+6+8=20s，评分路径上太久"）——**同类风险在 realtime 这条路上没做同样收敛**。

**一个体积问题**：`interpret` 的 prompt 用 `json.dumps(result)` 把 `profit` + `profit_bands`(3 档) + `口径区间`(2 档) 这三套**几乎相同的成本字典**整份塞了进去（`agent_graph.py:1837`），而竞品那块反而是**特意裁剪掉明细**的（`:1770-1771`）。这直接抬高首 token 延迟。

### 4.3 方案

**第 0 步（必须）：先装计时器，别凭感觉优化。**
现在没有任何阶段计时，上面全是"按代码常数推断"。我建议先加一个轻量计时（每个阶段起止时间 + 写进日志/「执行过程」面板），跑几次真实分析，拿到**真实分布**再决定优化哪一项。否则很可能花力气优化了占比很小的一环。

**第 1 步（按"收益确定、风险低"排序的候选）**：
1. **裁剪 `interpret` 的 prompt**：只给中性档 + 区间两端，去掉重复的成本字典。低风险、直接减首 token 延迟。
2. **并行化 `analyze_node` 的 VLM 与竞品抓取**（`asyncio.gather`）：省 min(VLM, 竞品)。
3. **并行化 `render_analysis_dashboard` 的地图/写面板/PDF**：省最多数十秒（地图新位置时）。
4. **9 张瓦片并行下载**。
5. **收敛 `realtime.py` 的 retries 到 2**：消除最坏 60s 的病理路径。**这是隐患修复，建议无论优化与否都做。**
6. **PDF 落盘复用**（配合 §2）。
7. **前端"分析完成"主动通知**：把 2500ms 固定轮询改成"分析完成写标记 + 更短间隔/事件触发"，省 0~2.5s 观感。
8. **`score_site` 本地查询优化**：连接复用（`get_conn` 每次重建表/索引）、bbox 预筛代替全表扫描、`estimate_profit` 记忆化（同输入现在要算 6 次，加上两次二分共 30+ 次）。
9. **"快速模式"选项**：允许用户为 `interpret` 选一个更快的模型（现在默认已是 turbo，但用户若手动选了 pro 就慢）。

### 4.4 需你拍板
- **先测量再优化**（多一轮，但不会优化错地方） vs **直接上低风险的 1/2/3/5**（快，但可能不是最大头）？我建议**先测**——只要几十分钟，换来的是靶向优化。
- 第 5 项（realtime retries）我建议**无条件做**，它是个隐患不是优化。

## 5. 切换专家/自由对话时对话框跳回最上方

### 5.1 我的理解
每次点不同的专家、或切换自由对话模式，对话框（聊天区）会**自己滚回最上方**，你要它**别跳**。

### 5.2 根因（已定位到具体机制，且**不在滚动代码里**）

链路是这样的：

1. `switchExpert()`（`sidebar.js:2243-2260`）与自由对话按钮（`ensureFreeChatBtn` 内 `:2056-2064`）都调用 **`sendCmd()`**。
2. `sendCmd()`（`:932-960`）**把文本灌进真的 textarea 并真的点了发送按钮** → 于是它是一条**真实的用户消息**，Chainlit 的消息 store 必然更新、React 重渲。
3. Chainlit 自带的 autoscroll（bundle 里的 `mKn`，受 `config.toml:40,43` 的 `user_message_autoscroll` / `assistant_message_autoscroll = true` 控制）会执行：
   ```
   scrollTo({ top: 最后一条 user_message.offsetTop - 20, behavior: 'smooth' })
   ```
4. 而 `hideCmdBubbles()`（`:2377-2423`）为了让指令气泡不可见，把这些元素设成 **`display:none`**（`:2405`/`:2419`），命中的正是 `[data-step-type="user_message"]`（`:2397`）。

**关键**：元素 `display:none` 之后，`offsetTop` 变成 **0**。于是第 3 步算出 `top = 0 - 20 = -20`，被浏览器夹到 **0** → **滚到最顶**。

**证据补充**：项目里**没有任何** `scrollTo(0)` / `scrollIntoView`（`grep scroll` 全量只有覆盖层自己的两处 `scrollTop=0`，`:2477`、`:2505`），也没有任何滚动位置保持代码。所以这个跳动**不是项目主动写的，是"隐藏气泡"与"Chainlit autoscroll"撞出来的副作用**。

> 标注：`offsetTop=0 → 夹到 0` 这条因果链是**基于代码的推断**，需要实机打点确认时序（`hideCmdBubbles` 是否稳定发生在 autoscroll 之前）。第 0 步应先验证。

### 5.3 方案

**先验证**：写一个探针（临时脚本/控制台），在 `sendCmd` 前后打印滚动容器的 `scrollTop`、最后一条 user_message 的 `offsetTop`/`display`，确认因果链与时序。

**方案 A（推荐，治本）：改隐藏方式，让它"不占位但仍留在流里"。**
把对**外层消息容器**的隐藏从 `display:none` 改成"零高度但不脱离文档流"，例如 `height:0; max-height:0; overflow:hidden; margin:0; padding:0; border:0; opacity:0`。这样元素仍在流中、`offsetTop` 仍是"接近底部"的真实值 → autoscroll 会滚到底部（也就是正确位置），**不会跳顶**。
好处：不需要"保存/恢复"这种对抗性逻辑；坏处：要确认气泡确实不可见（可能有 0~1px 残留，需实测）。

**方案 B（兜底，与 A 可叠加）：记录 + 恢复滚动位置。**
`sendCmd` 之前记录 `scrollTop` 与"是否原本贴着底部"；在 `hideCmdBubbles` 的 rAF 链之后恢复——原本在底部就回到底部，否则恢复原 `scrollTop`。
优点：无论上面哪种原因都能兜住。缺点：如果 autoscroll 的 smooth 动画还没跑完就恢复，会有轻微打架感；要给 `behavior:'auto'` 或加帧延迟。

**方案 C（补强）：把这类指令干脆不做成消息。** 更彻底但改动大——需要找到一条不经消息列表的通道（Chainlit 自定义 action / 后端静默接口）。**不建议本轮做**，风险高于收益。

**回归加固**：现有 UI 门禁（`chainlit-ui-verify` skill 的 `verify_ui.py`）加一条断言：**切换专家/自由对话后，聊天区 `scrollTop` 与操作前一致（容差 ±20px）**。这样以后不会回归。

### 5.4 需你拍板
- 用 A 还是 A+B？（我建议 **A 为主、B 兜底**，双保险且都不改架构）

## 6. 专家系统与"直接用大模型"到底有没有区别

### 6.1 我的理解
你想知道：我点这些专家，跟我直接把问题丢给大模型，**实质上有没有区别**。如果只是换一段人设文字，那专家系统就是虚的。

### 6.2 结论：**分三档，其中 3 位确实形同虚设**

先说**组装链路**：`compose_system_prompt()`（`src/experts/registry.py:279-295`）只拼三样东西——**公共铁律（`_common.md` 13 条）+ 该专家 persona 全文 + kb 检索结果**。它**不接受也不拼"证据包"**；证据是靠各节点自己作为 user message 传的。

| 专家 | 真实差异来源 | 判定 |
|---|---|---|
| **rent_negotiator**（租金谈判） | 拿到 58 同城挂牌分布 + `rent_limits`（盈亏平衡月租/回本达标月租上限），**裸 LLM 拿不到** | ✅ **真差异** |

2. **`free_chat` 路径上确实是"换人设"**（这正是你担心的场景）：用户选了专家后问一个非该节点的问题，走 `free_chat_node`，注入的证据只有**一行 `context` 摘要**（`f"品类: X, 地址: Y, 总分: Z, 结论: W"`，`agent_graph.py:1869/1875/1951-1953`）——**没有 score_result、没有竞品、没有租金行情**。除 kb 分区外，与裸 LLM 无异。
3. **仓库里没有任何一条测试对比"专家 vs 裸 LLM"**。`verify_experts.py` §1/§2/§6/§8 全是结构性断言（字段存在、源码字符串、图节点存在）；§4 只证明"检索结果不同"；唯一的 LLM 断言（§9，需 `VERIFY_EXPERTS_LLM=1`）**没有对照组**且默认不跑。**作者自己也承认**："`assertions` 只覆盖结构，不覆盖语气"（`src/experts/README.md:299-303`）、"话术质量未做质量抽检"（`docs/专家系统方案评估.md:260`）。

1. **给 `free_chat` 补真证据包**（最关键）：把现在的一行 `context` 摘要换成结构化证据 —— 至少包含 `score_result` 的关键字段（总分、四个维度分、预估月流水、租金占流水比、净利/回本/否决），竞品与租金证据按需带入。**这一步做完，"选专家"才第一次在主要路径上真正有差别。**

3. **让"硬约束"要么生效、要么删掉**（诚实原则）：
   - 低成本方案：把 `tools`/`forbids` 的**文本**注入该专家的 system prompt，作为明确的行为约束（模型自律，可测性弱但比现在"写了没人读"强）；
   - 高成本方案：真接 function-calling。
   - **或者**：承认它们是"设计期文档"，从运行时 schema 里去掉，只在 README 里保留说明。**我倾向"注入 prompt 文本"，成本低、效果可见。**
4. **处理 3 位"无 LLM 节点"的专家**（二选一，不要维持现状）：

5. **加一条可验证的差异化断言**（补上现在完全缺失的那一环）：同一问题分别跑"某专家"与"裸 LLM"，断言 **① 专家输出必须包含只有该专家证据包里才有的数字**（如谈判专家的"回本达标月租上限"的具体数值）、**② 裸 LLM 输出不包含**。这类断言涉及 LLM 自由文本，**按项目纪律只放网络信息性组，不进离线门禁**。
6. **顺带修两个小问题**：`competitor_node:2186` 的补充检索**不带 tags**（是全库检索，与该专家的分区声明不一致）；`state.py:52` 的注释仍写"当前分析的评分数据 JSON"，与实现（被覆盖成一行摘要）不符。

## 7. 综合评分改名「地址评分」+ 新增"能不能赚钱"的综合评分

### 7.1 我的理解
左/右栏那个「综合评分」，其实只是**这个地址好不好**（客群/竞争/交通/租金承受力加权），**并没有把"开了店到底赚不赚钱"合进去**。你要：① 把它改名为**「地址评分」**；② **另外新增一个真正反映"能不能赚钱"的综合评分**。

你的判断是**对的**，我用代码确认：

- 「综合评分」在代码里就是 `score_result['total']`，算法是四（五）个维度**加权求和**（`scoring.py:629-643`），权重来自 `config.py` 的品类画像（奶茶：客群 0.35 / 竞争 0.25 / 交通 0.25 / 租金 0.15；有面积时再加面积适配 0.10）。
- **成本与利润完全不在里面**：`total` 在 `:643` 就已定稿，而 `profit`（`estimate_profit`）在 `:717-729` 才算 —— 顺序上就不可能进总分。
- 租金只是以"**租金 ÷ 流水**"的分段给分进来（`scoring.py:230-242`），比的是租金与**营业额**，**不是租金与利润**。
- 代码注释自己就承认这个设计缺陷（`scoring.py:409-413`）："加权是**补偿性**的，位置分够高就能把 0 分补回来（这正是**总分 80.9 判推荐、月净利却是负的**的成因）"。
- 实测佐证：`public/dashboard.json` 里同一条记录 `total: 93.5`，同时 `月净利估算 -¥649`、`veto.触发 true`、`回本 40.8 个月`。**93.5 分写着"综合评分"，实际在亏钱。**

**"能不能赚钱"的数据其实已经全有**，只是散着：`profit['月净利估算']`、`profit['净利率']`、`profit['回本周期(月)']`、`profit_bands`（乐观/中性/保守三档）、`口径区间`、`rent_limits`（盈亏平衡月租/回本达标上限）、`veto`（一票否决）。

**顺带说明"一票否决"现在怎么工作**（改名时要一起处理）：它**不改 `total`**，而是改写 `verdict` 并写入 `veto`（`scoring.py:772-808`）。PDF 已经在做双轴呈现：未否决写「综合评分」，触发否决就改写成「位置分」（`report_pdf.py:232-241`）——**现在"综合评分"这个名字在不同分支下指代不同东西，本身就是混乱的**。

### 7.2 方案

**第一步：改名（低风险）**
把**展示层**的「综合评分」统一改为**「地址评分」**：右栏卡片 label（`app_chainlit.py:432`）、PDF 两处文案（`report_pdf.py:235/241`）、历史项摘要（`sidebar.js:2497`）。
- 字段名 `total` **不改**（改键会破坏历史 `analyses.json`、`conversations.json` 的兼容性）。这是纯展示改名，**向后兼容**。

**第二步：新增经营评分 —— 关键是把口径定死**

我不建议只给一个"神秘数字"。三档净利、口径区间、一票否决这些**都是真实的不确定性**，用一个 0~100 分盖住它们，等于制造新的假精确。所以给你三个方案选：

| 方案 | 形态 | 说明 |
|---|---|---|
| **A. 单一分数（你要的形式）** | 一个 0~100 的「经营评分」 | 由**中性档**的净利率与回本周期两项映射。需要你定权重与分档 |
| **B. 分数 + 区间（推荐）** | 「经营评分 62（保守 41 / 乐观 78）」 | 主分数用中性档，**同时并列三档分数**，与现有"三档情景""口径区间"的口径纪律一致——不把一个点估计伪装成确定值 |
| **C. 不评分，给结论块** | 「能不能赚钱」直接给：月净利区间 + 回本区间 + 租金余量 + 一票否决判定 | 最诚实，但没有"一个数"，可能不满足你的诉求 |

我**推荐 B**：既给你要的分数，又不丢不确定性。若你坚持 A 也可以，但**必须**在 PDF/右栏同时展示三档区间（项目里已有这条纪律）。

**如果选 A/B，需要定的是这张映射表**（我给出一个可用的初稿，请审）：

**经营评分 = 净利率分（60%）+ 回本分（40%），均按中性档计算**

| 维度 | 满分条件 | 0 分条件 | 权重 |
|---|---|---|---|
| 净利率 | ≥ 20% | ≤ 0%（即不赚钱） | 60% |
| 回本周期 | ≤ 12 个月 | ≥ 36 个月 | 40% |

**硬规则（与 §6.4 的一票否决保持一致）**：
- **一票否决触发时（月净利 ≤ 0 或回本 > 24 个月），经营评分封顶 59 分并标红**，不允许出现"位置好 + 经营评分 80"这种自相矛盾的展示；
- 无租金输入（用户没填月租）时，**不出经营评分**，显示"缺月租，无法判断"——**不猜**；
- 评分必须**附一句口径说明**（"基于中性档假设：物料 X%、人工 Y、外卖抽成 7.7%…"）。

**第三步：结论以谁为准？（必须一起定，否则会有两个"总分"打架）**
现在 `verdict`（推荐/谨慎推荐/不建议…）由 `total` + 否决共同决定。加了经营评分后，建议：
- **结论以「经营评分 + 一票否决」为准**（因为你的真实诉求是"能不能赚钱"）；
- 「地址评分」降级为一个**维度指标**（说明"这个位置本身好不好"），仍保留展示——它在谈判、找铺阶段仍有用。
- 需要一个明确的**优先级规则**：例如"经营评分 < 60 时，无论地址评分多高，结论都不是'推荐'"。

### 7.3 需你拍板
1. 经营评分用 **A（单一分数）/ B（分数+区间，推荐）/ C（不评分只给结论块）**？
2. 上面的映射表（净利率 60% / 回本 40%，阈值 20% 与 12/36 个月）**是否认可**，还是要改阈值？
3. 结论以**经营评分**为准（地址评分降为维度指标）——**是否同意**？
