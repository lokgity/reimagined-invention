## 三、双算怎么消的：做法、检验、量级

### 3.1 做法（一行之差）

| | 定义 | 问题 |
|---|---|---|
| v6 | `DP = D × P(真实 own_S, 真实竞品 S)`，`uplift = median(DP_store ÷ 商圈中位DP)` | P 的分子是 own_S，分母与自家品牌无关 ⇒ uplift 重复表达 own_S；而流水里 own_S 已经通过 P 计入一次（`scoring.py:701` → `estimate_monthly_sales`），`brand_factor` 在 `scoring.py:331` **又乘一次** |
| v7 | `DP_blind = D × P(自己 own_S := 1.0, 竞品 S 保持真实)`，`uplift = 1 + w·(median(DP_blind ÷ 商圈中位DP_blind) − 1)` | 度量"**假设该店没有品牌力**，它还比同商圈中位店好多少"＝位置/竞争微区位残差，与 own_S 正交 |

`w = n/(n+5)` 收缩、`MIN_N_UPLIFT`、`UPLIFT_CLAMP` 全部沿用 v2 原值，**只改了 own_S 是否置 1 这一处**。

### 3.2 检验（§2，零 API 可复现）

| 相关系数 | v6 | **v7** |
|---|---|---|
| `Spearman(own_S, uplift_raw)` | +0.6719 | **+0.1531** |
| `Spearman(own_S, uplift_final)` | +0.6599 | **+0.1055** |

raw 偏离 1.0 的幅度中位数：v6 **0.0804** → v7 **0.0468**。
⇒ 共线基本解除，uplift 现在提供的是 own_S **之外**的信息。

## 四、下游连锁：案例 F（天一广场 ¥12,000 蜜雪）——三口径对照

uplift 直接乘在流水上（`daily = base × (dp/ref_dp) × area × city × brand_factor × 0.6`），
换口径必然带动每一个数。下面三个版本**只差 `UPLIFT['蜜雪冰城']` 一个数**（其余参数全不动）：

| uplift | 月流水 | 日单量 | 测算人数 | 净利率 | 回本 | 经营评分 | 结论 | 免租月净利 |
|---|---|---|---|---|---|---|---|---|
| v1 = 1.1343 | ¥99,552 | 291 | 3/2 | 10.31% | 12.6 月 | 70 | 谨慎推荐 | ¥22,265 |
| v6 = 1.1903 | ¥104,467 | 305 | 3/2 | 12.15% | 11.0 月 | 76 | **推荐** | ¥24,688 |
| **v7 = 1.0018** | ¥87,923 | 257 | **2/2** | 11.71% | 12.6 月 | **74** | **谨慎推荐** | **¥22,292** |

**两个必须一起讲的非直觉点：**

1. **流水掉了 11.7%，免租净利反而略高**（¥22,292 > ¥22,265）。不是笔误，是**产能台阶**：
   v7 日单量 257 落在 **2 人产能档**（人均 140×2 = 280）内 ⇒ 测算人数从 3 降到 2，
   少扣一个人工。⇒ **净利不是流水的单调函数**，这是 `scoring.py` 里写明的预期行为。
2. **v6 的"推荐"完全由双算贡献**。v6 §5.4 就预告过"若换成品牌盲残差，本案例会回到谨慎推荐"——
   本轮实测确认。这也说明：uplift 换口径后，**历史上任何引用过"推荐"的对外材料都需重新核对**。

### 口径区间（v7 实测）

| | v6 | **v7** |
|---|---|---|
| 单量刚性端 | — | 营业额 ¥87,923 / 净利 ¥10,292 |
| 营业额刚性端 | — | 营业额 ¥123,401 / 净利 ¥22,022 |
| 不稳定租金窗口 | ¥22,000~¥36,500 | **≈¥22,300~¥34,000** |

`sidebar.js` KB③ 的"实测"note 已换成 v7 数，并**保留了 v1/v6 旧值留痕** + 产能台阶（2 人档）提醒。

## 六、⚠️ 门禁变红的两处（都不是放宽，是反转/加固）

### 6.1 `verify_brand_card.py` —— 唯一一个因 v7 变红的套件

```
FAIL verify_brand_card.py  rc=1
  assert any(c['brand'] == '蜜雪冰城' and c['tier'] == 'TIER1' for c in pl['cards'])
```

这条断言的**使命**是"证明 TIER 列真的在渲染"，v6 时代拿蜜雪当样例（它当时是 TIER1）。
v7 下蜜雪降 TIER2 —— 断言红得**正确**，说明 v7 真的生效了。
处置（反转 + 加固，不是删掉）：

- 改成钉死 v7 的**全部** TIER1：`assert _t1 == ['乐乐茶', '瑞幸', '茶百道']`（比原来只查一个品牌更严）；
- 蜜雪改为断言"仍在卡片里 + tier==TIER2 + `abs(uplift-1.0018) < 5e-5`"（值锚照旧钉死）；
- docstring T3 行注明 v7 名单。

### 6.2 `live_ui_probe.py` 的两个隐患（离线门禁挡不住）

1. **跨表面一致性升级**：卡片百分比必须 `== (知识页表值 − 1)×100`，
   且知识页表值必须 `== 引擎 UPLIFT[瑞幸]`（容差 5e-5）。
   行匹配不再靠 `'1.25'` 这种**巧合**（v6 时 CI 上界恰好含 "1.25"），改用列名 `'TIER'` 挑行。
2. **新加的引擎 import 暴露了一个脆弱点**：探针没有把 `src` 放进 `sys.path`，
   按文档用法直接跑会 `ModuleNotFoundError: No module named 'engine'`，**整轮探针中断**。
   已修：① 头部 `sys.path.insert(0, str(ROOT/'src'))`；② 该 import 包 try/except，
   失败时只把这一条判 FAIL、**不再炸掉整轮**。

**实机复验（重启 Chainlit 后）**：**52 PASS / 0 FAIL**。关键读数：

```
知识页 UPLIFT 行   瑞幸 1.1591 TIER1 55 1.017 ~ 1.250
品牌卡             3 瑞幸 已标定 引力 2.2 · 起步投入约 40 万 加盟品牌 同商圈流水溢价 +16%（区间 1.017~1.25） n=55
跨表面一致性       表值=1.1591  引擎=1.1591
卡片百分比         +16% == (1.1591 − 1)×100   ← 动态取数，不是写死文案
蜜雪/古茗/喜茶卡    0%（1~1.036）n=173 ／ −1%（0.958~1）n=218 ／ +5%（1~1.086）n=41
```

（`+16%` 是 `round((1.1591−1)×100)=16` —— 与 v6 的 `+25%` 同一条动态公式，改了表就自动跟着变。）
