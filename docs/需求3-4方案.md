## 一、需求 3：店铺优先的反推流程

### 1.1 现状与缺口

现有 `classify_node` 只认两条主路径：

- `have_shop` = **有铺子 + 有品类**（收集品类/地址/租金 → 分析）
- `no_shop` = **找商铺**（品类 + 地区 → 搜索推荐）

缺的是第三种：**有铺子，但没想好做什么**。用户手里握着租约，需要的是「这个位置适合开什么」，而不是「哪里有铺子」。

### 1.2 入口识别

新增 `_wants_shop_first(text)`：

```python
# 触发条件（二者之一）
#  A. 有铺子措辞 + 无任何品类词 + 有"不知道做什么"的语义
#     "我有个铺子但不知道开什么" / "店面租下来了，做什么好"
#  B. 直接问品类："这里适合做什么生意" / "开什么店好"
```

必须与 `_has_specific_shop` 区分开：**有铺子 + 提到品类 → 仍走原有 `have_shop`**（用户已经想好了，不该被反问）。

### 1.3 新增节点

| 节点 | phase | 职责 |
|---|---|---|
| `collect_shop_first_node` | `shop_first` | 收集 **地址 / 月租金 / 面积**，缺什么问什么，一次问全 |
| `reverse_match_node` | `reverse_match` | geocode → 四品类并联测算 → 排序 → 出卡片 |

**明确不做的事**：不收集品类、不收集前期投入。前期投入在品类确定之后再问（因为四个品类的投资额差一个数量级，提前问没有意义）。

优先级：**面积 > 租金 > 地址**。面积缺失时无法算面积适配度与流水规模；地址缺失则整个测算无法启动。三者齐备才触发测算。

### 1.4 测算与排序口径 ⚠️ 核心方法论约束

**问题**：不能直接比四个品类的总分或竞争分。

理由（与本项目已确立的统计诚实原则一致）：

1. `P_REF` 竞争分锚点**只有奶茶品类标定过**（83 家真实门店）。甜品/便利店/早餐在 `REF_DP` / `P_REF` 里都取 `'默认'` 口径，即沿用奶茶的 0.5012 —— 这是**没有依据的借用**。
2. 四个品类的 POI 关键词不同 → 竞品基数结构不同 → `P = A/(A+B)` 的绝对值天然不可比。
3. 总分里竞争分占较大权重，所以**总分同样不可跨品类比较**。

**采用方案（推荐）**：按**预估月净利**降序排序，回本周期作辅助。

- 净利 / 回本周期是**绝对量纲**（元、月），跨品类可直接比较，不依赖任何锚点口径。
- 竞争分**仍照常计算但只作单品类内的参考**，卡片上明确标注「竞争分跨品类不可比」。
- 四维度分（客群/竞争/交通/租金）全部照常输出，但**不参与排序**。

卡片上的推荐度标签由净利 + 回本周期共同决定：

| 标签 | 条件 |
|---|---|
| 首选 | 净利排名第 1，且回本周期 ≤ 24 个月 |
| 可选 | 净利为正，回本周期 ≤ 36 个月 |
| 谨慎 | 净利为负，或回本周期 > 36 个月 |

（阈值待你确认，暂定上表。）

### 1.5 卡片设计

新增 `kind = 'category-rec'`，复用现有卡片骨架（序号圆标 → 内容 → 箭头）：

```
① 奶茶  [首选]
   月流水 ¥15.8万 · 月净利 ¥3.2万 · 回本 18 个月
   周边 3 所学校、写字楼密集，年轻客流占比高
```

- 4 张卡片，按净利降序
- 底部小字：`竞争分基于各品类独立口径，跨品类不可比，仅供单品类内参考`
- 复用现有 `write_dashboard` / `public/sidebar.js` 通道，新增 `renderCategoryRec(d)`

### 1.6 选中后的分流

| 用户选择 | 后续 |
|---|---|
| 奶茶 | **复用任务 D 的品牌卡片**（`kind='brands'`），零新增成本 |
| 甜品 / 便利店 / 早餐 | 直接进 `collect_invest`（问前期投入 + 人数） |
| 都不满意 | 回 `shop_first`，允许用户指定品类 |

### 1.7 成本

| 环节 | API 调用 |
|---|---|
| geocode 地址 | 1 次高德 |
| 四品类竞品 POI | **0 次**（本地预抓取库优先，`get_surrounding` 已实现） |
| 配套类 POI（适配理由用） | 0~N 次（本地无数据才兜底） |

在浙江 11 市覆盖范围内，净增成本 ≈ 1 次 geocode。

## 二、需求 4：自由对话修复

### 2.1 病根（已定位，确凿）

`src/agent/agent_graph.py` 的 `classify_node` 第 3/4 步：

```python
# 3) 通用：触发了业务关键词 -> 按"有具体商铺/找商铺"分流
elif has_specific:
    phase = 'have_shop'
elif has_cat or has_addr or has_region or _wants_find(user_msg) or _wants_restart(user_msg):
    phase = 'no_shop'
```

**只要句子里出现品类词或城市名，就直接进流程，完全不判断是不是在提问。**

`_looks_like_question()` 这个函数**只在 `prev_phase` 分支里被调用**（第 2/2.5/2.7 步），主判定路径压根没用。

### 2.2 实测会翻车的输入

| 用户输入 | 命中 | 实际走向 | 期望 |
|---|---|---|---|
| 奶茶店毛利率一般多少？ | 品类词「奶茶」 | `no_shop` → 反问"你想开在哪个区" | 直接回答 |
| 便利店要办什么执照？ | 品类词「便利店」 | `no_shop` → 进流程 | 直接回答 |
| 杭州开店租金什么水平？ | 「杭州」+「开」 | 流程 | 直接回答 |
| 开奶茶店需要注意什么风险？ | 品类词 + 「开」 | 流程 | 直接回答 |

### 2.3 修法：主判定前插入「咨询闸门」

```python

    '设备', '货源', '工资', '人工', '税务', '合同', '转让', '趋势',
    '前景', '风险', '手续', '流程', '政策', '补贴', '注意什么', '好不好做',
]

# 新增：明确的"要开始选址"启动词（权重高于咨询词）
def _wants_start_flow(text):
    # 想开/要开/开一家/帮我找/推荐/我有个铺/看中了/分析一下/月租/租金是 ...
```

判定顺序调整为：

```
1) _wants_compare                       → compare
2) prev_phase 分支（基本不动）
3) 【新】if _wants_start_flow           → 原有 have_shop / no_shop 判定
4) 【新】elif 含 _CONSULT_KEYWORDS
           or _looks_like_question      → chat
5) 其余                                  → 原有 has_specific / has_cat 判定
6) _awaiting_answer 保持追问             → 原逻辑
7) else                                  → chat
```

### 2.4 取舍原则

**闸门偏松进 chat。** 理由：

- 误判进 chat 的代价小 —— `free_chat_node` 的 system prompt 已经写了"如果涉及选址，可以温和引导用户提供品类+区域"，LLM 会把用户带回来
- 误判进流程的代价大 —— 用户只想问个问题，却被连环盘问地址租金，体验直接崩

所以遇到"既像提问又像要开店"的模糊输入，**一律判 chat**。

### 2.5 必须保证 100% 进流程的输入（回归测试清单）

- 我想开奶茶店
- 帮我找杭州滨江的铺子
- 我有个铺子，月租 8000
- 杭州滨江春晓路 60 号，月租 8000，40 平，想开便利店
- 我想在宁波开个早餐店

### 2.6 兜底：手动开关（建议一并做）

在输入框旁（模型选择器附近）加「自由对话」toggle。打开后 `set_free_chat_mode(True)`，`classify_node` 直接返回 `phase='chat'`，跳过所有流程判定。

规则闸门再准也有漏网，手动开关是最后一道保险，实现成本很低。

## 三、附带建议：`llm.py` 超时隐患

**现象**（用户实测）：选 DeepSeek 模型后，界面「等待模型响应」长达 8 分钟无返回。

**两个叠加原因**：

1. **`DeepSeek-V4-Flash` 没有关闭 thinking**
   ```python
   # 豆包 pro 专门加了 thinking disabled，注释写着"实测 60s+ 不返回"
   _ARK_EXTRA = {'max_tokens': 1600, 'thinking': {'type': 'disabled'}}
   # 但 DeepSeek-V4-Flash 那一项漏了
   'DeepSeek-V4-Flash': (..., {'max_tokens': 1600}),   # ← 缺 thinking
   ```

2. **降级链串行重试，最坏 5 × 120s = 10 分钟**
   `_provider_list()` 依次尝试 已选模型 → 豆包pro → 豆包turbo → mimo → DeepSeek，每个 `timeout=120`。全程 Chainlit 只是转圈，**没有任何"正在尝试第 N 个模型"的反馈**。

**建议改法**：

- 给 `DeepSeek-V4-Flash` 补 `thinking: {'type': 'disabled'}`
- 降级链加**总超时预算**（如 180s），超预算就抛异常走规则兜底解读
- 每次切换 provider 前 `await _emit(state, 'tool', 'LLM 降级', ...)`，让用户看见进展

## 6.4 实施中发现并修掉的 3 个真 bug

> 都不是新写的代码引入的，是**既有缺陷**在本轮被测试暴露出来。

1. **`shop_first` 阶段补信息会掉出流程**（最严重）
   `classify_node` 没有 `prev_phase == 'shop_first'` 分支，用户在补充地址/租金/面积时会被通用分支按品类词改写成 `no_shop` → 图走到 `collect_info` 而不是 `collect_shop_first`，**流程直接断掉**。修法：新增 2.6 分支保持 `shop_first`。

2. **带门牌的详细地址被判成"在找铺子"**
   `_has_specific_shop` 第 3 步用 `extract_address(text)` 的结果判门牌特征，但该函数**只提取到区域级**，会把「杭州滨江春晓路 60 号」压成「滨江」→ 门牌特征丢失 → 判为 `no_shop`。
   修法：改用原文正则 `\d+\s*号` 判断，并排除"帮我找/推荐"类搜索意图（避免"滨江路100号附近有哪些奶茶店"被误判）。

3. **店铺优先分支定位精度退化**（影响最大）
   `parse_request` / `_clean_area` 都会把地址压到区域级，导致 geocode 拿到**区域中心点**而非铺位本身。
   实测同一铺位（月租 9000、45㎡）：
   - 用区域中心点 `(120.213, 30.21)` → 甜品净利 **¥108,659**、回本 1.8 个月
   - 用精确坐标 `(120.221068, 30.178233)` → 奶茶净利 **¥7,576**、回本 16 个月
   **相差 14 倍，且结论反转**（前者的"首选甜品"是假的，因为中心点恰好落在核心商圈，客流被虚高）。
   修法：`_extract_full_address()` 从原文重抽含门牌地址；classify 在 `shop_first` 阶段跳过 `_clean_area`。
