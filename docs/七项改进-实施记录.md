Python 3.12 + Chainlit，而离线门禁跑在 3.14，那段算术留在原文件里就永远测不到。

### 三个必须知情的实现事实
1. **Chainlit 2.11 没有 `cl.UserMessage` 类**（`hasattr` 为 False，`chainlit.utils`
   的注册表里没有这个名字）。用户气泡的**唯一**可行写法是
   `cl.Message(content=..., type='user_message')`（`type` 接受
   `'user_message' | 'assistant_message' | 'system_message'`）。
   —— 方案里"方案 A：用 `cl.UserMessage`"的前置技术验证在此**不通过**，改用等价通道。
2. **回放只渲染、不进 graph**，所以不会触碰 `state['messages']`。若写状态，
   同一次打开重放一次就翻倍累积。
3. Chainlit 只能**追加**消息，无法把更早的记录插到上方 —— 所以"查看更早"这一批
   在视觉上排在下方，批次说明里**必须明说**「时间上**早于**上方内容」，
   否则用户会读成顺序错乱。

### 验证（实机，非静态）

- ✅ `#zl-page-ov` 未 open（无中间覆盖层）

## 4. 分析耗时：先测量，再提速

### 第 0 步：计时器（`agent_graph.py::_Stage`）
把每个阶段耗时写进 `hooks['stage_ms']`（跨节点共享），并汇总成一条

已埋点：`评分引擎` / `门头照VLM` / `竞品挖掘` / `看铺‖竞品(并发段)` / `RAG检索` / `LLM解读`。

⚠️ 计时器里 `LLM解读` 走 `finally` 而不是 try 尾部：降级到规则解读同样耗了时间
（等完整个 provider 链才放弃），漏记会把"最慢的一次"正好藏起来。

UI 侧（`render_analysis_dashboard`）另打一行 `[timing] 工作台渲染 …` 到控制台 ——
**刻意不写进 `hooks['stage_ms']`**：那本账是"分析阶段"的，混进渲染会误导归因。

### 并发合并纪律（这次最容易出错的地方）
`analyze_node` 里两个分支**都要改 `result`**：VLM 经 `apply_storefront()` 返回一个
**新副本**，竞品往 `result['competitor_insight']` 写字段。
→ 若在并发里各改各的，先返回的副本会把另一分支后写进去的字段**整块覆盖掉**，
而且**不抛异常**，只会"静默少一块数据"。
→ 因此：**并发只负责取数**（`_vlm_probe` / `_competitor_probe` 都不碰 `result`），
**合并放在 await 之后按固定顺序做**。固定顺序还有个好处：`hooks['steps']` 里的事件次序
确定，离线回归才好断言。

### 第 3 步：顺手修掉的账本 bug（`run_agent`）

想让计时器**可回归、可比较优化前后**，就得跨轮复用同一本账：
`run_agent(msg, state, hooks)`。但 `run_agent` 原本写的是
`hooks = hooks or {}` —— 传入的空 dict 是 **falsy**，会被静默换成一个新 dict，
调用方**永远拿不到** `steps` / `stage_ms`（实测：拿到的永远是"最后一轮"那点数据）。
改成 `if hooks is None: hooks = {}`。
同因：结果里补一个**可序列化**的 `result['stage_ms'] = dict(hooks['stage_ms'])` ——
`hooks` 含回调、必须剥离，不补这一份就"跑完即失"，无法事后分析分布。

## 5. 切专家/自由对话不跳回最上方

### 根因（已定位，不在滚动代码里）
`sendCmd` 发的是一条**真用户消息** → Chainlit 自带 autoscroll 执行
`scrollTo(最后一条 user_message.offsetTop - 20)`；而 `hideCmdBubbles` 把该气泡设成
`display:none` → 它的 `offsetTop` 变成 0 → `scrollTo(-20)` 被夹到 0 → **跳顶**。

### 双保险
- **A（治本）**：`hideCmdBubbles` 改用 `softHide()` —— `height:0;maxHeight:0;overflow:hidden;
  opacity:0;pointerEvents:none`，**零高度但留在文档流**，`offsetTop` 仍有真实值，
  autoscroll 自己就算对了。
- **B（兜底）**：`captureScroll() / restoreScroll() / guardScroll()`，在静默指令前记
  滚动位（区分"原本贴底"），发出后连 rAF 两帧 + 80/240/600/1000ms 各还原一次。

### ⚠️ 实机发现并修掉的**真 bug**：兜底层原本全程空转
Chainlit 聊天区在 DOM 里是**两层同源 class 的容器**：
```
外层 div.relative.flex.flex-col.flex-grow.overflow-y-auto.zl-chatcol   ← 不滚（over=0）
内层 div.flex.flex-col.flex-grow.overflow-y-auto.zl-chatcol            ← 真正滚（over=3202）
```
两者都带 `zl-chatcol`（`ensureChatCol()` 故意给所有匹配列都加，为了底色铺满），
加不加该类都区分不开；而 `querySelector` 返回的是**外层** →
`captureScroll` 永远读到 `top:0`、`restoreScroll` 写进去纹丝不动。
**症状不报错，只表现为"偶尔还是跳顶"。**

修法：`scroller()` 在候选里挑**溢出量最大**的那个；都不溢出时取最后一个（等价）。

### 验证（实机）
- 前置条件先证明"这次点击真的生效"：当前专家 `category_reverse → site_advisor`、
  步骤节点 20 → 21；
- 然后 scrollTop **5265 → 5265**（完全不变）。

## 6. 专家系统：真接 function calling，做出可验证的壁垒

### 实现

2. **工具注册表**：新增 `src/experts/toolbox.py` —— 每位专家的 `tools`/`forbids`
   从"写在 md 里没人读"变成**真约束**（`allowed_tools()` 白名单 + `run_tool()` 分发，
   白名单外的调用被拒并如实回话，不编数字）。
3. **三位"形同虚设"的专家接上 LLM**：新增 `_expert_commentary(expert_id, user_msg)`，
   让 `category_reverse` / `storefront_auditor` / `franchise_advisor` 各自用**自己的人设**

   失败返回空串 → 调用方保持引擎模板文案（**严格增量**，不会让功能变差）。
4. **`free_chat` 补结构化证据包**：`build_evidence_pack(state)` 把会话里已算出的

5. **修 `interpret_node` 人设错位**：解读一份选址评分本就该是"选址评估师"的工作，
   固定用 `DEFAULT_EXPERT`；改前按"当前选中的专家"取人设，于是选了"模型审计师"就会
   用审计师人设 + 模型边界的 kb 分区去解读选址评分 —— 那不是"专家被拒绝"，是**用错了人**。

### 离线开关（必须知情）

### 壁垒的可验证证据（`test_expert_functioncalling.py`，网络信息性组）
同一个问题，两条路径：

| 路径 | 结果 |
|---|---|
| **专家路径**（带 tools） | trace: `brand_uplift ok=True` → 回答原样复述系统标定值 **1.134** |
| **裸 LLM 对照**（无 tools） | 「很抱歉，我当前没有权限调用 `brand_uplift` 工具，无法为你查询到蜜雪冰城的同商圈溢价系数，拿不到相关数据。」 |

**一个有真数据、一个如实说拿不到**。

⚠️ 纪律：断言只锁"工具真的被调用 + 数值原样出现"，**不锁裸 LLM 的措辞**
（项目纪律：不对 LLM 自由文本锁定措辞）。

## 7. 双轴评分：地址评分 × 经营评分

### 口径（定稿）
- **地址评分** = 原「综合评分」（`total` 键名不动，保兼容），含义是"**这个位置本身好不好**"，
  结构上不含成本与利润。
- **经营评分** = `business_score(profit, bands, veto_triggered, has_rent)`："**这个租金下能不能赚钱**"。
  净利率 60% + 回本周期 40% 线性映射（净利率 0%→0 分、≥20%→100 分；
  回本 36 月→0 分、≤12 月→100 分）；一票否决**封顶 59**；
  **无月租 / 无面积 / 无前期投入 → 不出分**（不猜，把原因写在卡上）。
- **结论以经营评分为准**（否决优先）。

### 实现
引擎 `scoring.py` → 看板 `app_chainlit.py` → PDF `report_pdf.py` → 历史摘要，四处贯通。
PDF 双轴文案：否决时 `位置分：{total}（{位置分结论}）` + `{经营评分文案}` + `综合结论：{verdict}`。

### ⚠️ 实机发现并修掉的问题：三种"没有经营评分"被合并成一句
历史会话卡片上原先把三种情况都显示成「不出分」：
1. 字段在、有分数 → 应直接显示；
2. 字段在、分数为 None → 应显示 **不可得原因**（真的算不出：无月租/无面积/无前期投入）；
3. **字段压根不存在** → 说明这条结果生成于**旧版本引擎**（本功能上线前存盘）。

改前 ② ③ 落到同一句话，于是历史会话上写着"不出分"，看着像"这个铺子算不出来"，
实际是"这份分析早于该功能" —— 两种含义完全不同（也可能在答辩时被当成 bug）。
现在 ③ 显示「经营评分（本结果未含）→ 旧版本结果，请重新分析」，
结论卡标注「选址结论［旧版本·仅地址］」，证据表里给出重算建议。

顺带修：卡片 label 是**纯文本渲染**（不解析 markdown），所以 label 里写 `**加粗**`
会原样显示出星号（实机截图踩到）→ 改用方括号强调。

## 8. 回归与门禁

新增 `src/analysis/verify_ui.py`（**已注册进离线门禁**）。它分两层：
- **静态断言**：对 `sidebar.js` / `app_chainlit.py` / `agent_graph.py` 的源码文本断言。
  挡不住"逻辑写错"，但能挡住**回退** —— 本项目真正出过的事故就是"改 A 处忘了 B 处"
  （softHide 与 autoscroll、两处知识库表面、指令白名单 5 处 `indexOf`）。
  **断言跑在"去注释"文本上**：说明性注释会提到被否定的旧函数名，带注释断言会自己打倒自己；
  而为了断言把注释删干净，下一个人就再也搞不清为什么不能改回去。
- **逻辑断言（真跑）**：`agent/replay.py` 的批次算术直接 import 真跑，
  断言"多轮拼接严丝合缝、覆盖 `[0,total)` 恰好一次、脏 shown 被夹住"。

门禁现状（`run_regression.py`）：**离线 14/14 rc=0 且 FAILED=0**；
网络信息性组 3 个（`test_vision_storefront` / `test_composite_intent` /
`test_expert_functioncalling`），其中 `test_composite_intent` 复跑即 PASS，
属于典型的网络 flaky —— 这正是它们**不进离线门禁**的原因。

实机验证脚本 `_live_ui_probe.py`（一次性诊断，**不进**门禁：要起服务 + 依赖真实会话数据，
天然 flaky）。运行前提：`C:\Python312\python.exe _live_ui_probe.py`，服务在 8502。
Playwright 启动方式**必须**显式给 `channel='chrome'`：默认的 `launch()` 走
`chromium_headless_shell`，本机只装了完整 chromium（`chromium-1223/chrome-win64`），
会直接 "Executable doesn't exist"。项目自己生成 PDF 时也是这么绕的。
